# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Verbo is

Verbo is a web-based Chinese-language learning platform. It combines live tutor booking, a structured study plan, podcasts with transcripts, OCR-based text scanning (photo/upload Chinese text → Pinyin + English translation), and spaced-repetition flashcards. Every word encountered in any module (Scan, Practice, Podcast, Study) auto-saves to one shared personal flashcard bank — this cross-module flashcard sync is the core product idea tying the modules together.

Planned modules: Scan (OCR), Practice, Find Tutor, Podcast, Study, Flashcard Bank.

Hover-then-shortcut is the established save pattern for read-only word displays (Read, and any future module that renders tokenized text): hovering a word shows a pinyin/translation tooltip, and pressing **Alt+1** while hovering saves it to the flashcard bank — there is no click-to-save. That tooltip is the shared `components/WordPopover.jsx` (prefix `wp-`) — a styled `position: fixed` card that clamps to the viewport edges and flips below the word when there is no room above — used by `ScanDocument`, `ReadArticle` and `PodcastEpisode`. Each of those pairs it with a token class (`sd-token` / `rd-word` / `pe-word`) whose `.active` state mirrors `:hover`, so the highlight and the popover are driven by one piece of state and cannot disagree. **`StudyUnit` currently has no hover-translate at all**: `hoveredWordRef` is still declared and read by its Alt+1 listener but nothing ever assigns to it, because the Reading rework replaced the annotated `reading_tokens` render with plain per-character spans over `study_text_lines`. Restoring it needs the backend to annotate each line's `chinese` the way `ArticleController::show` does. The popover's saved state is scoped to the current page view, so its footer says "Saved", never "in your flashcards" — nothing on the page knows what the bank already contains. `ReadArticle.jsx` tracks the hovered token in a ref (`hoveredWordRef`, updated on `onMouseEnter`/`onMouseLeave`) read by a single `keydown` listener, avoiding stale-closure issues without re-subscribing the listener per hover.

## Architecture

Two-app monorepo, functionality-first (no visual design/styling applied yet — plain unstyled HTML elements throughout):

- `frontend/` — React (Vite), React Router for pages, plain `fetch`-based API client (`src/api.js`), auth state in `src/context/AuthContext.jsx` (token kept in `localStorage`)
- `backend/` — Laravel 9 API, Sanctum token auth (not SPA cookie auth — the frontend sends `Authorization: Bearer <token>`), SQLite for local dev (`database/database.sqlite`)

**Working features: Auth, Flashcard Bank, Scan (OCR), Read, Find Tutor, Podcast, Study, Dashboard.** This is the pattern to replicate for the last remaining module (Practice):
- Backend: `routes/api.php` → `Api\AuthController` (register/login/logout/me), `Api\FlashcardController` (index/store/destroy), `Api\ScanController` (index/store/show), `Api\ArticleController` (index/show/store/update/destroy), `Api\TutorController` (index/show/store), `Api\BookingController` (index/store), `Api\PodcastController` (index/show/store/update/destroy), `Api\StudyLevelController`/`Api\StudyUnitController`/`Api\StudyVocabularyController`, `Api\QuoteController` (show/store), all under `App\Http\Controllers\Api`. Flashcards belong to a user via `User::flashcards()` / `Flashcard::user()`; ownership checks must cast IDs (`(int) $model->user_id !== $request->user()->id`) since SQLite returns foreign keys as strings — a bare `!==` silently 403s the rightful owner.
- Every scan is persisted (`scans` table: `user_id`, `original_filename`, `raw_text`, `words` json, `size_bytes`) — `size_bytes` must be read off the `UploadedFile` *before* the OCR block, since the `finally` deletes the upload and the size can never be recovered afterwards; it is nullable, and scans predating it render an em dash in the Documents table — Scan is a saved-document history, not a one-shot ephemeral result. `ScanController::index` returns lightweight list rows, `show` returns the full record (same shape `store` returns). The upload area is a drop zone with a queue: photos arrive by browse, drag-and-drop or **Ctrl+V paste**, all three funnelling through one `addFiles()` so the size limit and its wording cannot drift between them. Scanning runs the queue **sequentially** (OCR is CPU-bound and the endpoint shares the 300/min bucket); one photo navigates to its document page, several stay put against a refreshed list. Progress uses `api.scanWithProgress`, an XHR upload — `fetch()` cannot report upload progress — and the row flips to an indeterminate sweep once the bytes are sent, because OCR time is not measurable from the client and a bar sitting at 100% would be a lie. **Results always render on their own page** — `ScanDocument.jsx` at `/scan/:id` — never inline on the index: clicking a row in the Documents table links there, and a finished upload navigates there too, so a fresh scan and a reopened one are the same screen rather than two divergent UIs. `ScanController::show` and `destroy` are ownership-gated with the usual `(int)` cast, so a scan is only viewable and deletable by the account that made it. Delete needs no file cleanup — `store` already removes the upload once OCR finishes, so the row is all that persists. Both delete entry points (the hero button on `ScanDocument`, the row's ⋮ menu on the index) arm on the first click and act on the second; the page-level one disarms after 4s on a timer rather than on blur, since blur never fires if focus never landed on the button. `show` also runs `DictionaryService::annotate()` on `raw_text` (same as Read/Podcast/Study) and returns `tokens`, so the scanned text gets the identical hover + Alt+1 save treatment — `saved` is keyed by the word string and shared with the aside's Save buttons, so a hover-save also flips the matching list row. **Scans can be shared by public link** (`scans.share_token`, nullable + unique; null means private): the row's ⋮ menu offers Open / Share / Delete, and Share opens a dialog with the link, Copy, and Stop sharing. `POST /scans/{scan}/share` is **idempotent** — it returns the existing token rather than rotating it, so a link already sent out does not silently die when the owner reopens the dialog — and `DELETE /scans/{scan}/share` revokes, which breaks every copy of the link instantly. `GET /shared/scans/{token}` is the one Scan route **outside** `auth:sanctum`: the token is the credential, so it is 40 chars from `Str::random`. That response is hand-built rather than `$scan->toArray()` because it goes to anyone on the internet — it must never carry `user_id`, the token, or the row id; only filename, text, words, created_at and the annotated tokens. The recipient's page is `pages/SharedScan.jsx` (prefix `ss-`) at `/shared/scan/:shareToken`, mounted outside both `ProtectedRoute` and `Layout` since the visitor has no account and there is no sidebar to render; hover-translation works there but **Alt+1 saving does not**, because saving needs a flashcard bank to save into. The Documents table's "Shared Users" column is no longer `N/A` — it reads Private / Anyone with link off `share_token`. The page splits text left / word list right (sticky aside), mirroring `StudyUnit`'s reading layout since the content has the same shape; "Save all" iterates sequentially rather than `Promise.all` because the flashcard endpoint shares the 300/min bucket.
- Frontend: `src/pages/{Register,Login,Dashboard,Flashcards,Scan,ScanDocument,Read,ReadArticle,FindTutor,Podcast,PodcastEpisode,Study,StudyLevel,StudyUnit}.jsx`, `src/components/{ProtectedRoute,Layout}.jsx` — `Layout` renders the sidebar (see **Navigation** below) and gates the authenticated area via nested routes in `App.jsx`; `AuthProvider` wraps the app in `main.jsx`. `/` redirects to `/dashboard` (the landing page after login), not `/flashcards`.
- **Dashboard is a read-mostly aggregator, not its own data domain**: it pulls from `GET /tutors` (Recommend Teachers, first 3), `GET /articles` (Top Reads), `GET /podcasts` (Pick up + the Podcasts row) and `GET /study-levels` (the study tile in Pick up) — no new endpoints, just client-side `.slice()` on existing lists. The one piece of its own data is `quotes` (a table with a single row, id 1) — `QuoteController::store` always upserts that one row rather than creating per-user quotes, since the quote is global and admin-edited, shown to every user via `GET /quote`.
- **Layout is measured off `design/dashboard/Dashboard.jpg`** (the newer export — `design/Dashboard.jpg` is an earlier, simpler version, superseded). Full-width hero, then a two-column body: a left content panel and a right rail, `749fr / 420fr` with a 26px gutter, held as `fr` so the 1.78:1 split survives any width instead of only matching at the export's size. Both panels are white with a 1px `#c8c8c8` outline; inner cards use the 1px `#2b2644` navy the rest of the app uses. Sampled colours: hero/duration-badge/peak-bar `#7d76a0` (the duration badge is the one outline on the page that is **not** the shared navy — it strokes `#544d77`, `--db-duration-edge`), "Unit" tag `#bcb3e8`, level tag `#fe916a`, activity bar `#d5c6ff`, "View all" pill `#a89ce3`, section bar `#8d87ad`, cover placeholder `#cccbd1`, page `#f9f8fe`. The Pick-up row (`.db-pickup`) **fits the panel rather than scrolling** — the design runs it off the edge, but a visible scrollbar there was unwanted, so the three tiles hold the export's 327 : 209 : 209 proportions as flex weights against a `0` basis and share whatever width there is. `min-width` floors (260 / 175) make the row wrap on a narrow panel instead of crushing the tiles, so it is capped at the study tile plus two podcasts. Don't reintroduce `overflow-x: auto` here **on a wide screen**: it forces `overflow-y` to compute to `auto` too, which clips the cards' hover lift and shadow. **Below 1150px it DOES scroll, deliberately** — that is where the body drops to one column and the panel can no longer hold the row, so the overflow has to be reachable rather than merely hinted at, and the fade mask comes off with it (a gradient over the edge hides the peek of the next card, which is the thing that says the row moves). The hover-shadow trade-off is accepted there because a touch screen has no hover.
- **Large parts of the Dashboard design have no backend and are explicit placeholders**, grouped as `PLACEHOLDER_*` constants at the top of `Dashboard.jsx` so it is obvious what is real: podcasts have no duration or author column (`8mins` / `Chen Mingyue` / language line), tutors have no lesson count or rating (`275 Lesson` / `4.9 Rating`), there is no enrolment or schedule table at all (**My Course**), and until recently nothing recorded time spent — **Stats Summary is real now**: `activity_days` (`user_id`, `day` as a plain Y-m-d string, `seconds`, `last_beat_at`, unique on user+day) is fed by `POST /activity/heartbeat`, which `hooks/useActivityHeartbeat.js` calls once a minute from `Layout` (so every authenticated page is covered). The beat **carries no duration**: `ActivityController::heartbeat` credits the gap between beats measured server-side and clamps it to 120s, so a client cannot inflate the one number on this page a user might want to game, and time asleep/hidden is dropped rather than back-filled. The client only beats while the tab is visible AND there has been input in the last 5 minutes, so a page left open overnight does not count. `GET /activity/summary?days=N` (N clamped 1..31) returns one bucket per day including empty ones, so the chart always has seven bars. **`ActivityDay.day` must NOT be cast to `date`** — the cast writes back `Y-m-d 00:00:00`, so a `firstOrCreate` keyed on `Y-m-d` never matches and inserts a duplicate on every beat. The unrelated `GET /activity` (a recent-activity feed derived from flashcards/scans/bookings) still exists but no page uses it. **The streak badge is real too** — derived from `activity_days`, not a new table: `ActivityController::streaks()` walks the descending day list and rides along in the `/activity/summary` response, so the badge costs no extra request. A day counts if it has a row **at all**, not if it clears a minimum — the first heartbeat of a day credits 0 seconds by design, so a threshold would deny credit to someone who genuinely turned up briefly. The run may end **today or yesterday**, so the badge does not read 0 all morning before the user opens the app; it only breaks once a full day is missed. The query is capped at 400 rows since nothing older can affect a current streak. Reads "N day streak" — attributive, never "N days streak" — and drops to a greyed "No streak yet" when the run is broken. **The flame and the label each carry their own `position: relative` nudge, and neither is decoration**: flexbox centres each item's LINE BOX, but neither glyph's visible ink is centred inside its own line box — and they are wrong by *different* amounts, which is why the text did not sit on the flame's line. `.db-streak-text` takes `-2.87px` and `.db-streak-flame` takes `-1.14px`, each its own measured error, landing both ink centres on the badge's centre (16.18 / 16.18 / 16.17). The label is wrapped in its own span purely so it can be nudged without dragging the flame with it. Two things that do NOT work here, both tried: padding (shifting the pad moves both glyphs together, so it can centre one or the other but never align them to each other), and `line-height` (half-leading is symmetric, so the ink-to-line-box offset is constant whatever the line height). If the balance ever looks off again, change those two px values — not the padding. And **"Pick up where you left off" IS real resume state, and it is ONE recency order across modules** — `recent_views` (`user_id`, polymorphic `viewable_type`/`viewable_id`, `last_viewed_at`, unique on the triple, indexed on `user_id + last_viewed_at`) records everything a user opens. It **replaced the study-only `study_progress` table**, because the row mixes study units and podcasts and orders them by when they were last opened: "what did I touch most recently?" is one question across modules, and two per-module tables would have to be merged in PHP on every dashboard load with no way to order them in SQL. The old table is still on disk holding the pre-migration copy of the data — its model, controller and routes are gone, nothing reads or writes it, and it can be dropped once this has bedded in. `StudyUnit.jsx`, `PodcastEpisode.jsx` **and `ReadArticle.jsx`** ping `POST /recent-views` with `{type, id}` on load, fire-and-forget so a failure never blocks the page. **`RecentViewController::TYPES` is a whitelist, not a free-form morph map** — the type comes off the request, so without it a caller could point a row at any model in the app and have the Dashboard render it. **Opening an article writes to TWO tables and neither is redundant**: `article_views` feeds the recommender ("has this person read things like this?"), `recent_views` feeds this row ("what did I touch most recently?"). Neither can answer the other's question. The read tile (`.db-read-tile`) is the podcast card's shell — width, padding, radius, border, shadow and cover height all measured identical, since they sit in one row — carrying the topic cover it already wears on Read, a format badge, and a reading time. It deliberately has **no duration badge**: that figure is a placeholder on the podcast card, and copying a placeholder onto a new card is how a stand-in becomes a fact. `GET /recent-views?limit=3` returns them newest first, each shaped for its own tile and tagged with a `kind` the client switches on; it over-fetches and drops rows whose target was deleted, so a stale row never blanks a slot. It returns an **empty array, not 204** — the Dashboard pads the row either way, so nothing has to branch on emptiness. **Every card keeps its OWN design size wherever the recency order puts it** — a study card is always `327px`, and a **podcast card is the same card here as in the Podcasts section below** — same width *and* height — so it takes that section's `.db-grid3` sizing, `max(190px, calc((100% - 40px) / 3))` against the same panel width, rather than the pick-up row's own 209. Cards are set by type (`.db-pickup > .db-study` / `> .db-pod` / `> .db-read-tile`), never by slot. **The `max()` floor is not decoration**: once the body drops to one column the panel is ~410px, and the bare fraction is a 102px card — narrower than its own cover, with the title in an 81px column. 190 is the width the phone layer independently settled on for this card. A 2px `#7d76a1` outline on these cards was tried and **reverted** — they wear the same 1px navy as every other card on the page. (Note if it is ever revisited: `border-box` pins the *width*, not the height, so a thicker border made the pick-up podcast card 2px taller than its twin in the Podcasts section and broke the same-height rule; it needs the padding re-cut to `9px 9px 11px` to hand that pixel back.) Both the `Unit n` and `HSK n` tags are **60x30 at 12px, radius 8, with a 2px stroke**, and 60px is a **floor, not a fixed width** — the pair still measures exactly 60/60 for the labels it was designed around, since "Unit 1" and "HSK 3" both sit inside 40px of content box, so they remain the matched pair the design draws. It stopped being a hard width because a **Daily Use level is named for its situation**: "Ordering Food" needs 78px, and at a fixed 60 the text ran out of the pill and was sliced off by the card's edge mid-word. Growing lets `.db-study-tags`, which already wraps, drop the longer tag onto its own line instead; `text-overflow: ellipsis` is the backstop beyond that. (This is also why the tag is `display: block` with `line-height: 30px` rather than a grid — a grid item cannot take `text-overflow`.) Each stroke is each a deeper cut of its own fill rather than the page navy (`--db-tag-unit-edge` `#7d76a1`, `--db-tag-level-edge` `#dd7753`) — a shared outline colour would flatten the pair into one kind of tag. Drawn as an **inset box-shadow rather than a border**, so the pills do not grow and pull the tag row taller against a title pinned to exactly two lines. **`.db-pickup > * { min-width: 0 }` is what makes those widths actually hold**: a flex item defaults to `min-width: auto` (its min-content width), and `.db-pod-title` is `white-space: nowrap`, so a long title's full unwrapped width became the card's floor and blew it far past its set width — a card with a long title rendered ~380px against a short one's 236px. The 3-up grid below never showed this because `minmax(0, 1fr)` already floors its columns at 0. Watch for it when testing: a row of short titles hides the bug completely. The row is `align-items: flex-start`, not `stretch`: stretching pulled the podcast up to the study card's height and broke that match, so each card type keeps its own natural height (327x225.9 against 236.4x220.4) and they align along the top. Two other approaches were tried and rejected: positional `327 : 209 : 209` flex weights, and stacking the study card in the narrow slots. Both made the same mistake — resizing the card to fit the row, so the same unit looked different depending on what you had clicked last, and at 209px the study card's fixed 135px cover left ~27px of clipped title beside it. **The row is not made to fit; its overflow FADES.** `.db-pickup` is `flex-wrap: nowrap` + `overflow: hidden` under a right-edge `mask-image` gradient, so the cards run past the panel and dissolve into it. This needs no "is it overflowing?" test: a short row ends before the fade region and nothing visible fades. Note the row overflows essentially always — the design's own `327 + 209 + 209 + 40 = 785` already exceeds the 749 panel, which is what "the design runs it off the edge" meant. **The vertical padding (`14px 0 28px`) with a matching negative margin is load-bearing**: both `overflow: hidden` and the mask clip to that box, and the hover shadow (`0 8px 20px`) reaches ~12px above and ~28px below the card, so without the padding the lift gets shaved off. The negative margin cancels it so nothing moves. For the same reason, don't reach for `overflow-x: auto` — it forces `overflow-y` to compute to `auto` too and brings the clipping back. **Text that does not fit FADES rather than cutting to an ellipsis** — `text-overflow` is `clip` everywhere in this row and a `mask-image` gradient does the work: sideways on `.db-study-quote`, downwards on the multi-line titles. The horizontal masks need no overflow detection at all, because the gradient only bites where text actually reaches the edge — a short title is left untouched. **`.db-pod-title` is two lines now, not one nowrap line fading sideways**: episode titles are authored `中文 - English`, and on a single line the English half — the half that says what the episode is about — was always the half that got cut.

**A downward fade needs CLEARANCE, and this was wrong everywhere at first.** Pinning a box to exactly the number of lines its text uses puts the last line *inside* the fade's ramp, so a title that fits comes out visibly greyer than the line above it and reads as truncated. Every vertical fade here therefore sizes to `lines + ~0.7em`: `.db-pod-title` and `.db-read-tile-title` are `3.3em` for two lines (`4.65em` for three on a phone). Measured on the read tile: 3.7px of clearance before, 13.2px after, against a 10px ramp. The softening then only appears when there is genuinely another line.

**And the sharper form of that rule, learned by getting it wrong again on the Read banner: a fade mask is only safe on a box with an INDEPENDENT height, and `max-height` does not give one.** `.rh-title` carried `max-height: 3.2em` with a comment claiming the usual `lines + 0.7em` clearance — but a maximum is not a height, so with one or two lines the box collapsed to exactly its text and the ramp ate the glyphs every time. A one-line title had the bottom of its own descenders and its question mark faded out. When the box is sized by its content, clamp it (`-webkit-line-clamp`) instead; the usual objection to the clamp — that it makes `scrollHeight > clientHeight` unconditionally true — only matters where something tests that element for overflow. Note the row's real proportions land ~4% off the design's ratio because **`flex-basis: 0` resolves against the content box**, so each tile's padding (10px on podcasts, 14px on study) rides on top of its share; the design only ever depicted a study-led row, where it measures 1.54 against the drawn 1.565. Suggestions pad the row when real history cannot fill it — a new user has none — but they always sit **after** real history and never duplicate something already in it: unit 1 of the **most-populated** level plus the newest podcasts — `StudyLevelController::index` now returns `units_count` (via `select(...)->withCount('units')`, not `get([...])`, which would drop the subselect) so the Dashboard can pick the level with the most content instead of whichever sorts first, and empty levels never surface in the tile. Its study tile is built from a **unit**, not a level (level cover + `Unit N` + level title + the unit's English title + its Chinese line), which needs a second call: `GET /study-levels` omits units, only `GET /study-levels/{id}` loads them, so the tile is chained after the list and fails soft. Unit titles are authored as `中文 - English` but **inconsistently spaced** (`接你们 - We` and `接你- We` both exist), so the split matches the first dash with optional surrounding space and only treats it as a split when the left half contains Han characters — an English title with a hyphen is left intact. Building any of these for real means a new tracking subsystem, not a new query. The chart **scales to the busiest day**, which is drawn dark, and the dashed rule marks the **weekly average**, sitting below that bar as `design/dashboard/Dashboard.jpg` draws it. The rule's height and its label must always agree — a line drawn below the peak but labelled with the peak would be a lie — so "below the tallest bar" and "marks the average" are the same decision, not two. Known trade-off, and the reason this briefly marked the peak instead: on a lopsided week (one busy day, six quiet ones) the average lands near the floor. The dark peak bar is what identifies the best day. The bars and the rule live in a shared `.db-plot` box: `.db-chart` carries the padding for the chip above and the weekday labels below, so if the rule positioned itself against that padded box its percentages would resolve against a different height than the bars' and it would miss the bar top by ~37px. Both ratios are computed from `seconds`, not the rounded `hours` field: at small totals the 2dp rounding is a large fraction of the value and would put the average line visibly off its true position. Do not floor the scale at one hour (an earlier version did): it pinned every bar to the bottom until a user had logged a full hour, which read as a broken chart with the average line stuck on the floor. Durations are labelled in minutes below an hour — "0.01 hours" carries no information on a real early week — and **zero is its own case**: the `Math.max(1, ...)` floor that stops a real but tiny session reporting as zero was also catching genuinely empty days, so an untouched day read "1 min"; it now reads "No time". **Hovering a bar shows that day's total** (`.db-chart-tip`), positioned just above its own bar via an inline `bottom: calc(min(H%, 100% - 30px) + 6px)` — the clamp is what keeps the peak's label inside the plot instead of colliding with the hours total above it. The whole COLUMN is the hover target, not the bar: a five-minute day is a two-pixel sliver nobody can point at, and an empty day has no bar to hover at all. It replaced a native `title`, which takes a second to appear and cannot be positioned. **Z-order in the plot is deliberate and fragile**: bars paint at `auto`, the dashed rule at `3` so it is drawn ON TOP of the bars (a rule that vanishes behind the tallest bar cannot be read against the one day it most needs comparing to), and the hover tip at `4`. `.db-chart-col` must stay at `z-index: auto` — giving it one creates a stacking context that traps the tip inside it, underneath the rule.
- **`articles.type` is a FORMAT and `articles.category` is a TOPIC** — they answer different questions and are no longer used interchangeably. Format is article/story/funfact and appears only as a small badge on a card's cover. Topic is what the piece is about (Everyday Chinese, Culture, Entertainment, Stories, Travel, Business) and is what the Read page is organised by. Mixing them is what once put "Grammar" beside "Entertainment" in one filter row as though a reader were choosing between them; a piece can be an Article about Culture, so one list could never hold both. Grammar and Food were retired as topics in that pass — the grammar pieces are all about how Chinese is actually spoken, which is what Everyday Chinese means here.
- **`Trending` is a pill, and it is NOT a topic** (`src/trending.js`, offered on both the Read topic row and the Dashboard's Top Reads format row). It sits beside `All` because those two are the entries that cut the list a different way rather than naming a value of the column the other pills come from. The ordering lives in one shared module on purpose: two copies of "what counts as trending" is how the Dashboard and Read end up telling a reader two different stories about the same library. **Articles with no likes are dropped, not sorted to the bottom** — ordering the whole library by a column that is zero for most of it is the default list under a heading claiming otherwise, so an unliked library gets an honest empty state instead. The pill's value is `__trending`, never the word, so it cannot collide with a real `articles.category` of that name. No backend work: `index()` already ships `likes_count` via `withCount`. The note under the heading states the ordering, because the card carries no like count and the grid would otherwise be in an order the reader cannot account for.
- **Article titles are authored `中文 - English`** ("Why Chinese films happen at the 饭桌 (dinner table)"), which is why several one-line card titles across the app had to become two: on a single line the English half — the half saying what the piece is about — was always the half that got cut. Podcast titles follow the same convention.
- **Read home is a shelf page, not a filtered grid** (`pages/Read.jsx`): no page title *block* — a heading over a line of copy explaining what a reading page is for pushed the first article most of a screen down. The page is named by `.rd-title` inside the topbar instead, which costs no vertical space; what stays refused is a heading band of its own with explanatory copy under it. (The original reason for having no title at all was that the Podcast/Reads toggle above already said Reads; that toggle is gone.) Then a two-row control bar (search + Saved pinned right, topic pills across the full width beneath) and `Recommended for You` followed by one shelf per topic, three cards each behind a `View all`. **Topics are PILLS, not a dropdown** — they are the page's primary cut of the library, so hiding the whole list of what Verbo publishes behind a click was backwards; search is drawn differently because it is the escape hatch for someone who already knows what they want. The two rows are measured, not stylistic: at 1440 the content column is 875px against 788 for the pills plus 359 for the search group, so sharing a row forced the pills to wrap *around* the search box and strand three on a second line. **Nothing on this page uses `--rd-indent`** — the topbar, divider and icon buttons all sit at the page gutter, so a 30px tab-in gave the page two right edges 30px apart, which is what made the top read as inconsistent; all four edges now measure 0.00px apart. `.rd-panel` keeps the indent, since it belongs to ReadArticle and SavedArticles.
- **Every article generates its own cover** — now `components/ArticleCover.jsx` (prefix `ac-`), not `Read.jsx`. - New Eloquent `create()`/`updateOrCreate()` calls don't reflect DB-level column defaults on the returned model (SQLite doesn't round-trip them) — set defaults explicitly in the controller before `create()`, not just in the migration. Same root cause bit both `Flashcard.source_module` and `Booking.status`.
- Setting a foreign key that isn't in the target model's `$fillable` (e.g. `TutorProfile.user_id`) via a raw `Model::updateOrCreate(['user_id' => ...], $data)` silently drops it — mass assignment protection applies even to the match/attributes array. Always create through the owning relation instead (`$request->user()->tutorProfile()->updateOrCreate([], $data)`), which sets the FK directly and bypasses `$fillable` for that column only — same pattern already used for `flashcards()`/`scans()`.

- `app/Exceptions/Handler::unauthenticated()` is overridden to always return a JSON 401 — the Laravel default falls back to `route('login')` when the request lacks an `Accept: application/json` header, which 500s here since this is an API-only app with no named `login` web route. The real frontend always sends that header so this never surfaced through the UI, only through bare `curl`/Postman calls. Don't remove the override.

CORS (`config/cors.php`) is locked to `http://localhost:5173`, `supports_credentials` is `false` since auth is token-based, not cookie-based.

**Rate limiting is split into two buckets** (`RouteServiceProvider::configureRateLimiting`): `api` is 300/min keyed by user id (or IP when logged out), and `auth` is 10/min keyed by IP and applied only to `POST /register` and `/login`. The general limit has to be generous because one page view fans out to several requests and React StrictMode doubles them in dev — the old shared 60/min tripped during ordinary browsing. Don't relax the `auth` bucket to match; it's the brute-force surface.

**A failed request must not end the session.** `api.js` attaches the HTTP status to every thrown error (`error.status`) and `AuthContext` clears the token *only* on a genuine 401. Before that, any failure — a 429, a 5xx, a network blip — hit the same catch-all and silently logged the user out, which looked like random logouts. A 429 also gets rewritten to a friendly "Too many requests. Please wait a moment and try again." instead of Laravel's raw "Too Many Attempts."

### Data fetching — one cache, and no page that blanks itself

`src/dataCache.js` + `src/useApiData.js`. Page switching was slow, and measurement said why: the deployed API answers most requests in ~200ms but **stalls 1-15s on roughly one request in three**, and every page threw away what it knew on arrival. Dashboard → Read → Dashboard refetched all eight Dashboard calls behind a blank `Loading...`.

- **`useApiData` seeds from cache during the FIRST render**, not in an effect. An effect runs after paint, which would flash the skeleton for a frame on every revisit and lose the whole point.
- **`loading` vs `refreshing` is the contract.** `loading` means nothing is known yet and is the only state that may show a skeleton — false on every revisit. `refreshing` means something is on screen and a fresher copy is on the wire. A revalidation that fails behind existing data is **swallowed**: replacing a good page with an error banner because a background refresh stalled is strictly worse than leaving it alone.
- **A 30s freshness window** (`FRESH_MS`) means a revisit inside it fires no request at all. Without it stale-while-revalidate still costs one request per mount, and this app shares a 300/min bucket across the whole client (React StrictMode doubles everything in dev). It is not a correctness mechanism — anything the client changes calls `invalidate()`, which drops the entry regardless of age.
- **The cache is keyed by RESOURCE, not by account, so it MUST be emptied whenever the account changes.** Otherwise the next person to sign in on this browser paints the previous person's dashboard from cache. All three sign-in paths funnel through one `startSession()` helper in `AuthContext` for exactly this; logout and 401-expiry clear it too. **Any new way to become a different user has to go through there.**
- **Keys are shared across pages on purpose** — Read and the Dashboard both use `articles`, Study/Find Tutor/Tutor Detail share `study-levels`, `tutors`, `bookings`. Arriving at Read from the Dashboard costs nothing.
- Pages that hold their record in BOTH state and a ref (ReadArticle, PodcastEpisode, StudyUnit, ScanDocument — the Alt+1 stale-closure pattern) were **not** converted to the hook; they seed their existing state from the cache instead. Rewiring them would have meant touching every mutation path for no gain.
- **Skeletons are static — no shimmer, no pulse.** Same rule as everything else here: an animation only advances while the tab composites frames, and a frozen shimmer reads as a broken page. `components/Skeleton.jsx`, prefix `sk-`.
- **The bell and messages pollers also go through the cache.** They render on every page, so remounting restarted their interval and refired immediately — a "one-minute poll" that actually cost one request per page switch (4 in dev, 2 in production). They pass their own poll interval as the freshness window.

Measured over six page switches: **5 requests on a fresh boot**, every page rendered. Previously each switch refetched its whole page plus the pollers.

### The phone layer — `src/mobile.css`, and the list that is easy to miss

One stylesheet, everything inside `@media (max-width: 767px)`, imported after `fonts.css` so it wins on equal specificity. It exists for what a phone does not get for free: `100dvh`, fields that do not zoom on focus, notch and home-indicator clearance, and navigation under a thumb.

**The trap worth knowing about**: it holds ONE list of every page container that drops to a 16px gutter, so twenty-odd stylesheets cannot drift. A page left off that list keeps its **90px desktop gutter on a phone** — 180px of padding — and renders as a sliver. **When a page looks like a narrow column on a phone, check that list before anything else.**

**It has two failure modes, and the second one hid five broken pages.** The obvious one is omission: `.td`, then `.sl`, then `.pe` — the episode page, whose card measured 195px inside a 375px viewport and whose title ran out past the card's edge. The subtle one is a listed selector that **matches nothing**: `.bo`, `.ms` and `.qp` were all present and looked handled, but those pages render `bo-page`, `ms-page` and `qp-page`, and no stylesheet defines the short forms at all. A dead selector is indistinguishable from a working one by reading — the file looked complete while Bookings, Messages, the quiz page, PodcastEpisode and Upgrade were all still at 90px.

So **audit it with a script, not by eye**: read the gutter block's selectors, read each page stylesheet's 90px container rule, and check the class is BOTH listed and actually rendered by that page's JSX (`className="…"`). That check now reports 21 gutter pages, 0 unhandled. When adding a page, copy its root class out of the JSX rather than guessing it from the prefix.

Related: don't implement a phone behaviour in a page stylesheet if this layer already handles it. The pick-up row's swipe scrolling lived in both for a while, at two different breakpoints, which is precisely how two implementations drift.

### The Railway volume — what survives a deploy

The container filesystem is discarded on every deploy, so `docker/entrypoint.sh` symlinks Laravel's writable trees onto a mounted volume at `/data` (`VERBO_DATA_DIR`). The SQLite database and **all** uploads live there.

- **It links `storage/app`, NOT `storage/app/public`**, and the difference was a real data-loss bug. The private uploads — `storage/app/chat` (message attachments), `storage/app/classwork` (assignment files and student submissions) and `storage/app/tutor-credentials` (certificates) — are **siblings of `public`, not children of it**, so linking only the public child left every one of them on the container filesystem. They were destroyed on each deploy while their database rows survived, and the app then rendered files that 404ed: a student's submitted essay became a row pointing at nothing. `scans` is the one exception that never mattered, since `ScanController` deletes the upload as soon as Tesseract has read it.
- **Moving the link up needed NO data migration.** The volume already stored images at `$DATA_DIR/storage/app/public`, and `storage/app/public` resolves to that exact path through the new parent link — the layout is unchanged, only the mount point moved up a level. There is a simulation covering the upgrade from the old layout in place.
- **`rm -rf "$link"` must never grow a trailing slash.** On a symlink, `rm -rf dir` removes the link while `rm -rf dir/` follows it and empties the target — which here is the volume holding every upload and the database. The loop also `continue`s when the link is already correct, so on an ordinary restart the delete does not run at all.
- **If no volume is attached, `/data` is just a container directory** and everything is ephemeral again, silently. The scripts assume the mount rather than checking for it, so confirm it in the Railway dashboard rather than inferring it from the app working.

### Publishing content to another environment

`content:export` / `content:import` (`app/Console/Commands`). Production has the schema and no rows — the whole library was authored against local SQLite — and copying that file wholesale is not an option because it also holds real accounts, tokens, private scans, bookings and chat.

- **Only the admin-authored library travels**: quotes, articles, podcasts, and the study curriculum with its images. Deliberately excluded: users, tokens, flashcards, scans, bookings, messages, conversations, notifications, recent_views, payments, enrolments, classrooms, preferences. A scan is a private upload and a booking is an agreement between two people; shipping either to a public server is a disclosure, not a migration.
- **Ownership is REMAPPED, never carried.** Exported rows reference local user ids that mean nothing elsewhere, so every `user_id` is repointed at one resolved owner. The importer **refuses to create that account** — one minted by a deploy script has a password nobody set, which is an administrator nobody controls.
- **Postgres does not advance a table's identity sequence** when a row arrives with an explicit id, so the next ordinary insert would collide. Sequences are reset after import; SQLite tracks the max itself.
- **Idempotent**, upserting on the primary key — and therefore **NOT wired into the entrypoint unconditionally**. It runs only when `CONTENT_IMPORT=1` is set on the service, because left on, every redeploy would silently revert anything edited through the admin UI in production. Set it, deploy once, remove it.
- **It has to run INSIDE the container.** `railway run` executes on the operator's own machine with the service's env vars injected, so the rows would reach Postgres while the images went to their laptop — production would have covers that 404. (It does not even get that far: the dev machine's PHP has no `pdo_pgsql`.)
- `--skip-level-category=daily` leaves Daily Use behind, and the exclusion **cascades** through `PARENTS`: dropping a level drops its units, vocabulary, texts, lines, grammar, examples, quiz questions and culture images. A child kept behind a missing parent is a foreign key pointing at nothing.

### Onboarding — five questions after sign-up, all of them optional

`pages/Onboarding.jsx` (prefix `ob-`) at `/onboarding`, built to `design/Verbo_Learning_Preferences_and_Onboarding.docx` (§3 steps 2-6 and §11's copy). **Inside `ProtectedRoute` but OUTSIDE `Layout`** — it is a focused flow, and a sidebar full of places to go is the opposite of what it is for.

- **Most of the spec was already built.** `learning_preferences` already covered §4.1-4.4 (level, HSK, goals, focus, styles/interests); only §4.5 `daily_goal` and §4.6 `study_time` were added. Don't re-derive this — check the model's option constants before adding a field.
- **`users.onboarded_at` is the gate, NOT the existence of a preferences row.** "Has this person been asked?" is a different fact from "what did they answer?", and someone who skipped every question has still been asked — deriving it would put them back in the flow on every load, punishing them for declining. Verified: skipping all five still stamps the flag and lands on the Dashboard.
- **Existing accounts were stamped at migration time**, so nobody already using Verbo is interrupted. This is new-sign-ups-only by decision, not by accident; a backfill is required whenever this column's meaning changes.
- **`ProtectedRoute` does the redirect**, guarded three ways: `user &&` (a failed non-401 `/me` leaves a token with no user, and redirecting on that would trap someone over a network blip), the `onboarded_at` check, and `pathname !== '/onboarding'` which is what stops the loop. Onboarding itself bounces an already-onboarded user to the Dashboard so the URL cannot be re-entered.
- **Nothing is saved until the end** — one `POST /learning-preferences` then `POST /user/onboarded`. Five separate writes would leave a half-filled profile behind for anyone who closed the tab midway, and these answers are read together or not at all.
- **Picking "Not sure" as a level clears `hsk_level`.** The HSK question is only shown for a known level, so answering it and going back would hide the field while keeping its value — saving "I don't know my level" alongside "HSK 4". Clear a conditional field with the thing that revealed it.
- **Design combines three of the supplied references**: Register's dark gradient panel (so sign-up and onboarding read as one flow), the second reference's vertical stepper inside that panel, and the fourth/fifth references' card — segmented progress, step counter, one question, `Back / Skip for now / Continue`. The ✕ on a selected chip is the first reference's one genuinely instructive detail.
- **Motion is ornament only.** `ob-in` is **transform-only** and the progress segments are a static class per segment, never a width transition — same rule as everywhere else in this codebase. The whole screen is readable and usable at frame 0.
- **THE RAIL SHOWS PROGRESS, AND THE CONNECTOR IS WHAT SAYS SO.** It was a flat `rgba(255, 255, 255, 0.18)` at every step, so the row drew five marks joined by a line that never changed: the marks said where you were and the line said nothing. `.ob-step.done::before` takes the accent now, driven by the same class the mark already uses.
- **STATE IS A CLASS; MOTION IS A DECORATION LAID OVER IT — and that split is what lets this page animate at all** when the Dashboard's goal bars and the Read banner could not. Two one-shot animations: `ob-trace`, a glint running the length of a connector as its step completes, and `ob-ping`, a ring expanding off a mark as it becomes current. **Neither reports anything the static rail does not already say**, so there is nothing to strand. Both rest safely: the glint is parked at `-18px`, *outside* the element, so a tab that never composites shows a plainly filled connector rather than a highlight halfway down one; the ring's frame 0 is a crisp outline at the mark's own size, which is a decoration looking firmer than the design's soft halo rather than a step reporting the wrong state. Verified by seeding both to `currentTime = 0`: the connector reads `rgb(168, 156, 227)` with the glint at `calc(0% - 18px)`.
- **The horizontal row needs its own keyframes.** Below 940px the connector turns sideways (`left: 27px; right: 0; height: 1px`), so `ob-trace-x` runs the band left-to-right against `ob-trace`'s top-to-bottom. Same construction, same parked-outside resting position.
- **The top progress segments got the same treatment**, keeping the rule they were written under. `.ob-seg.on` is still the state and still never a width transition; `ob-seg-lit` is a glint parked at `-30px` at rest. **Only the newly-lit segment plays it** — a CSS animation starts when its property is *first* applied, and the segments behind it have already had theirs. (Landing on step 4 directly does light all four at once, which reads as the bar filling.)
- **`ob-in` is 0.34s over 7px, up from 0.22s over 9px, and the direction of that trade is the point.** 220ms reads as a jump-cut rather than a movement, and the distance was doing work the duration should. The worst case for an entrance is content stranded at its start offset, so **the number that carries the risk is the DISTANCE, not the time** — 7px is a strictly smaller worst case than 9px, and the longer duration costs nothing there. Same bounded-displacement reasoning as the edit drawer's 24px nudge standing in for `translateX(100%)`.
- `prefers-reduced-motion` strips all three outright, which is safe precisely because the filled connector, the lit mark and the filled segment are static — removing the motion leaves the rail and the bar saying exactly what they said with it.
- **Verifying a one-shot animation in a pane that does not composite needs a probe, not a stopwatch.** `requestAnimationFrame` is throttled to whole seconds there, so "click, wait two frames, read" overshot a 500ms animation and `getAnimations()` came back empty twice. Appending a real `.ob-seg.on` element, finding *its* animation and seeking `currentTime` by hand is deterministic: measured `calc(0% - 30px)` → 37.8% → 68.5% → 90.7% → parked again, with the fill `rgb(168, 156, 227)` at every point.
- **Measuring optical centring: three ways to get it wrong, all of them hit.** A cap-band correction is only as good as the instrument, and a confident wrong number is worse than none — each of these produced a plausible value that moved a label the wrong way. (1) **Do not derive the box from `getBoundingClientRect()`.** `#root` carries `zoom`, and dividing by an assumed 1.1 is wrong whenever the surface renders at another scale — it reported a 19.96px chip as 19.38px, a 3% error that swamps a sub-pixel decision. Take padding, border and font-size from `getComputedStyle` instead; those are CSS px and immune to zoom. (2) **The cap band ends at the BASELINE, not at the ink bottom.** Subtracting `actualBoundingBoxDescent` makes a word with a descender measure differently from one without — under identical padding "Everyday Chinese" read 2.8px off while "Culture" read 0.00. If a metric's answer depends on which letters are in the label, the metric is broken. (3) **`await document.fonts.ready` before any canvas `measureText`**, and check `document.fonts.check()` — canvas silently falls back to a system font otherwise, and Hellix's ascent read 12.7 unloaded against 14.5 loaded. Finally, `line-height: normal` does NOT equal `fontBoundingBoxAscent + fontBoundingBoxDescent` (measured 16 against 16.9), so a used line-height has to come from a multi-line probe's `offsetHeight`, not from canvas. **A reading is only trustworthy when it is stable across repeated runs AND independent of the label's letters AND its box arithmetic closes.** Below about 0.5px, prefer leaving a value alone over "correcting" it.
- **MEASURE THE CAP BAND AGAINST A FLAT-CAPPED REFERENCE (`H`), NEVER THE LABEL'S OWN INK** — this is the sharpest form of trap (2) above and it was hit again on the Dashboard's `n / 3 done` pill and the sidebar's `Popular` tag. `actualBoundingBoxAscent` for `0 / 3 done` measures **0.71875 per em** against `Popular`'s **0.70313**, because round glyphs — `0`, `3`, `O` — overshoot the cap line by ~1%. Two pills in the same family would have been tuned by different amounts for a reason that has nothing to do with either. Every flat-capped letter (`H`, `E`, `I`, `T`) returns 0.70313 at both weights, stable across runs: that is the font's number, and it is the one to use. **Measure at a large size and scale down** — at the real 10.88px canvas quantises, reporting `cap: 8.00` exactly and yielding a too-round 0.5px error for both pills; at 400px it resolves properly and the true errors are **0.935px and 0.826px**. A correction computed this way lands in ONE pass rather than needing the three the Vocabulary Bank's pill took: both re-measured at **0.001px** with their box heights unchanged.
- **Every boxed label on this page carries a measured asymmetric pad**, and so do the Vocabulary Bank's pills. Hellix reserves more ascent than a short label uses, so symmetric padding centres the LINE BOX and leaves the glyphs ~1px low — visible enough that the user spotted it on the "Optional" chip. The corrections are measured on the **cap band** (cap top → baseline), never the ink bounding box, since a word with a descender would otherwise disagree with one without. Sub-pixel rounding under the 1.1 zoom means the value has to be **iterated and re-measured**, not computed once: the Vocabulary Bank's filter pill went 0.86 low → 0.5 high → 0.00 across three passes. Guessing a plausible-looking asymmetry is what produced the bug in the first place — measure it.
- **Deliberately NOT built** (asked and confirmed): §3 step 8's tutor/course recommendation screen — `RecommendationService` scores *articles* only, and scoring tutors and courses is a new subsystem, so onboarding ends at the §6 profile summary. And §9's Settings structure (Connected accounts, Payments, Support, Interface language, Pinyin/Translation display) — those have no backend, and the rule against placeholder features stands.

`LearningPlanCard` in `Dashboard.jsx` (prefix `db-plan-` / `db-goal-`), fed by `GET /learning-plan` (`Api\LearningPlanController`). Sits directly under the activity chart, and the order is the point: the chart says how much has been done, this says what is left.

A `daily_goals` table with a `progress` column would be a second source of truth that drifts the moment one write fails, the same reason "My Courses" computes its week from `starts_on`. The card reports lessons left at the pace the learner chose and lets them do arithmetic they can see. Asked and confirmed: *"dont do this"*.
- **AND NO XP.** It was proposed and dropped. The Dashboard already carries three real progress signals (the streak badge, the weekly hours chart, the mastered count), and a fourth score derived from these very goals is the same fact said twice — plus a number that buys nothing, which this app refuses everywhere else (Payment Methods, Attendance).

A minutes goal therefore needs a new subsystem. Making the heartbeat module-aware is the way to do it (a `module` on the beat plus a per-module day table, roughly 40 lines, reusing the server-side gap measurement untouched) — deferred, because a 5-minute goal also cannot be demonstrated live.
- **Targets are FIXED and live on the server** (`TARGETS`, `LABELS`), shipped in the response so the card cannot drift from what is counted — the same rule as `LearningPreference`'s option lists. Randomising them ("review 23 words") makes the day impossible to plan around; per-user difficulty tiers are a later idea that this shape does not block.

- **`Carbon::today()` in the app timezone**, the same boundary `ActivityController` uses for the streak and the chart. Two notions of "today" on one Dashboard would roll over at different moments.
- **"Whenever I have time" gets no pace, deliberately.** That option exists for someone who will not commit to a number (see the note on `LearningPreference::DAILY_GOALS`), so the subline shows lessons left with no rate rather than assuming one. `pace_label` is built server-side because the option strings do not groom by one rule — "15 minutes" + " a day" reads fine, "1 hour or more" + " a day" does not; it is `an hour+ a day`.
- **"Lessons opened", never completed** — nothing in the app records a unit as finished, so the stat is labelled `OPENED`, the same wording the Profile page uses. Current level is derived from the last unit opened, reusing `ProfileController`'s rule rather than adding a second one.
- **CHANGE sits on the STATS row, not beside the title, and that is load-bearing.** In the rail the card is ~171px of content at 1240px, so a link beside the heading left ~110px and broke "7 lessons left" across two lines mid-phrase. `.db-plan-top > div { min-width: 0 }` is the other half of that fix — a flex item defaults to its min-content width, the trap `.db-pickup > *` documents.
- **No transition on the goal bars' width.** An animation only advances while the tab composites frames, so a bar easing from 0 would sit at 0 in a backgrounded tab and report every goal as untouched. A completed row states itself in the accent rather than going grey — done is the good outcome and should not read as disabled.
- **A GOAL IS A TILE, and the reference it came from is a "Goal board".** Three bare labels over 5px hairlines was the flattest thing in the rail; each goal is now a tinted tile carrying a marked chip and a fat bar with its own number inside. **Two columns, not the reference's four** — measured, this card is **236.2px wide with 197.4px of content** at 1440, so a chip, a title, a bar and a tick side by side cannot be laid out here: the chip spans both rows and the tick moves into the bar, which has width to spare (the track measures 155.8px, the longest label 100.9px against a 142px column).
- **COLOUR CARRIES STATE HERE, NOT IDENTITY.** The reference gives every row its own hue; it owns a palette with three and Verbo owns lavender plus one warm accent, so a blue and a green minted to fill the gap would be exactly the second colour family the `#8b6ff0` sweep removed. **The glyph is what tells the three apart** (`GOAL_MARKS` in `Dashboard.jsx`, the app's 24 grid at `strokeWidth 1.7`, declared at their only call site).

The state is carried by **three changes within one hue**: the tile drops from `--db-pill-bg` to `--db-border`, the chip goes from white to the solid `--db-progress`, and the bar fills. It still steps FORWARD rather than greying — done is the good outcome and the app refuses to draw it as disabled. The lesson generalises: *a colour with a meaning on another page is not automatically consistent on this one.*
- **The difficulty pill beside the level is REAL** — `study_levels.level_label`, the admin-authored column Daily Use already reads ("Beginner level", "Upper intermediate level"). Nothing is inferred from the HSK number; deriving difficulty from curriculum naming is exactly what the Profile popover refused when it dropped its own "Intermediate" segment. `levelLabel()` strips a **trailing** " level" server-side beside `pace_label`, so the card's context does not say the word twice and a label authored without it is untouched. A long title ellipses rather than pushing the pill off the card — verified with "Ordering Food at a Restaurant" + "Upper intermediate": the row still cleared the card by 21.2px and did not wrap, because `.db-plan-level` carries `min-width: 0` + ellipsis and the tag is `flex: none`.
- **The three stats are STACKED tiles, not the mockup's side-by-side chip and number — measured.** This card is **236px wide at 1440** (259.8 painted), so a third of it is ~66px: a 28px chip plus the tile's padding leaves ~13px for the word and "OPENED" needs 40. The mockup is drawn on a canvas several times this wide. Stacking keeps the marked tile it is really asking for and fits — all three labels measure unclipped at the rail's real width. `CHANGE` is a tile like the others now rather than a link floated off the end, and its label takes the number's slot so the three stay the same height.

At **(0,1,1)** it outranks the chip's own **(0,1,0)** rule, so `display: flex` lost to `display: block`, the centring stopped working, and all three glyphs sat hard against the top of their circles with **13px of nothing beneath them** (measured: 0 above, 13 below). Nothing errored and the build was clean; it just looked like the icons were drifting upward, and it survived two rounds of screenshots before being reported as *"the book is going up"*. The label and the number carry classes now (`.db-plan-stat-label` / `.db-plan-stat-value`). **Grep for `^\.[a-z-]+ (span|strong|div|a|p) ?\{` before adding one** — the Dashboard's remaining type selectors all target `svg`/`img`, which no wrapper in this file is. Verified after: all seven chips on the page report `display: flex` with equal padding on all four sides.

The reserve is written as the two line boxes rather than a measured constant, `calc(1.15rem * 1.1 + 0.6rem * 1.25)` = 32.24px against the 32.23px the real stacked pair measures, which is also why `.db-plan-stat span` now states `line-height: 1.25` instead of leaving it at `normal` — an unstated line height cannot be added up. ### Vocabulary Bank — the flashcard bank, with where each word came from

`pages/VocabularyBank.jsx` (prefix `vb-`) at `/vocabulary`, laid out from a user-supplied Word Bank reference: a four-counter strip with tinted corner badges, a search field, source filter pills, then hairline-separated word rows carrying a state chip on the right. It **replaced `pages/Flashcards.jsx`** — `/flashcards` now redirects, and the sidebar's Tools item reads "Vocabulary Bank".

- **Reviewing happens INSIDE the bank; it is not a separate collection.** The learner never picks which words become cards, because everything they saved already is one. `components/VocabReview.jsx` (prefix `vr-`) is the run: Chinese first, then you decide, *then* you check — revealing before answering would let someone mark themselves right after seeing the answer, which makes the mastered count worthless. Space reveals, 1/2 answer.
- **`flashcards.source_type`/`source_id` is the point of the whole thing.** `source_module` already recorded the *kind* of place ("podcast"), enough to filter by but not to go back to. The pair points at the actual article/episode/unit/scan, and `example` keeps the sentence. `FlashcardController::SOURCES` is a **whitelist, not a free-form morph map** — the type comes off the request, same rule as `RecentViewController`. Both halves must be present or neither is stored; half a reference points at nothing and would be skipped forever on read.
- **The example sentence is captured at SAVE time, never derived later** (`src/sentence.js`, shared by Read/Podcast/Scan). The body can be edited or deleted afterwards, and a sentence recovered later might not be the one this learner actually read. `exampleFor` falls back from object identity to a text match so Scan's aside Save buttons — which hand over a row from the word *list*, not a token from the text — keep their context too.
- **A stale closure was silently dropping every source.** The Alt+1 listener on ReadArticle/PodcastEpisode/ScanDocument subscribes once (deps `[token]`) so it does not re-attach per hover, which means its handler closes over the FIRST render — where `article`/`podcast`/`scan` is still null. The word itself came from the hovered token and saved fine, so nothing looked broken; only the id was missing. Each page now holds the loaded record in a **ref** alongside the state, the same trick `hoveredWordRef` uses. Don't read the state in those handlers.
- **`store` still dedupes on (user, word) and now keeps the FIRST source too.** Meeting a word again does not change where you learned it — verified: re-saving 机会 from Scan returned 200 with the original Podcast source intact. Source and example are only *backfilled* onto a card that lacked them.
- **Mastery is a streak, not a total** (`Flashcard::MASTERED_STREAK`, 3): one right answer among many wrong ones says nothing, and the page states the rule on screen so it can be defended rather than felt. `lapses` only ever goes **up** while `correct_streak` resets to 0 on a wrong answer — that asymmetry is deliberate, since "this one is difficult" is a fact about your history that a single lucky answer must not erase. Mastery still wins over difficulty: a word you used to trip on but now answer right three times running is no longer the one to drill.
- **There is no `due_at` and no scheduler.** The counters track how a word is *going*, not when to show it next; spaced-repetition scheduling is a separate decision and is not built. The review buckets asked for — all / saved today / difficult / from one source — need none of it.
- **`learning` is `total - mastered`**, so the two counters always sum to the total. Two numbers that do not add up read as a bug even when both are right.
- **The reference's fourth stat was "Categories"; flashcards have none**, so that slot carries **Sources** — the number of distinct places words came from, which is real. Nothing on this page is invented.
- `GET /flashcards/stats` and `/flashcards/review` must be declared **before** any `/flashcards/{flashcard}` route or they bind as ids — the same trap `bookings/clear-past`, `notifications/read-all` and `articles/recommended` hit.
- `attachSources()` resolves a page of cards in **one query per type**, not one per card. A card whose source has since been deleted keeps its module label and loses only the link — the word is still yours.
- Search covers the **example sentence** as well as word/pinyin/meaning: "which word was in that line about the airport?" is exactly how someone looks for a word whose characters they cannot remember.
- **Opening a word shows sentences using it, found in the learner's OWN library** — `App\Services\ExampleFinder` behind `GET /flashcards/{flashcard}/examples`, rendered in the row's expanded panel. Not a dictionary lookup and not an external corpus: CC-CEDICT carries definitions rather than examples, and something like Tatoeba would be a network dependency returning sentences from nowhere the learner has been. Every example comes from an article, a podcast transcript, a study conversation or a scan already in the app, so each one links back to something they can open and read in full. **Study lines are searched first** — they are authored as teaching material, ship a human translation, and are the shortest; nothing else is translated, because this app machine-translates nowhere. **Scans are scoped to the owner**, unlike the other three: the rest is published material any account can already open, but a scan is a private upload and must never surface in someone else's bank. Fetched **on open, never with the list** — four LIKE scans per card against a table that grows without bound would be almost entirely wasted work. Sentence splitting is a lookbehind on the terminator with a negative lookahead for a closing quote (without it `走路要多长时间？”` split twice and shipped the sentence stripped of its own quote), plus `balanceQuotes()` for a mark whose partner stayed in the previous sentence. At most **two per source**, or one chatty lesson supplies all three. **The client's cache guard is a REF, not the `examples` state** — listing that state in the effect's deps made it cancel its own request: writing `{loading:true}` re-ran the effect, whose cleanup killed the first run's `live` flag, so the 200 was discarded and the panel stayed empty.
- **StudyUnit saves carry `source_type` but no `example`** — that page has no annotated token stream to pull a sentence from (see the hover-translate note above), and an invented one would be worse than none.
- **Every word row carries a ⋮ menu** (`.vb-row-menu` opens `.vb-rowmenu`): Open the source · Show details · Delete. Deleting used to live at the bottom of the expanded detail panel, so it was reachable only *after* opening a row — which is why nobody could find it — and it fired on a **single click**, the one delete in the app that did. It arms then confirms now, disarming on a 4s timer (blur never fires if focus never landed on the button). The ⋮ is always drawn rather than revealed on hover: being unfindable is what it was built to fix, and a touch screen has no hover.
  - **The button and the ⋮ are SIBLINGS inside `.vb-row-top`.** The row is itself a `<button>`, and a button inside a button is invalid — the inner one never gets its own click. That split also moved the hover tint and the accent bar from the button onto `.vb-row-top`, or the highlight would stop short of the menu and read as a half-lit row.
  - **`.vb-list` can no longer be `overflow: hidden`** — it clipped an open menu on the last row, the same trap the collapsed sidebar's flyout hit. The 16px corners are drawn on the first and last rows instead, in **longhand** (`border-top-left-radius` etc.), because a single-card list matches both `:first-child` and `:last-child` and the shorthand would leave it with only the bottom pair.
  - **The menu flips above the button when it would open off the bottom of the screen.** `window.innerHeight` and a `getBoundingClientRect()` are both painted viewport pixels, so they compare directly — the `#root` zoom only double-applies when a measured rect is written back *as a length* inside `#root`, which this never does. It sets a class; CSS does the placing.
  - **Two class-name collisions cost real debugging time here, and both are the same mistake.** `.vb-menu` was already the header's Review dropdown, so the row menu inherited its `top` and `width: 268px` — and an abspos box pinned top AND bottom with `height: auto` stretches between them, so it rendered a full viewport tall. Renaming to `.vb-rowmenu` fixed that and exposed the second: `.up` as a bare modifier **is the Upgrade page's root class**, which handed the menu `min-height: var(--app-vh)` and a 90px gutter. **Never use a bare modifier class in this codebase** — every page root is a two-letter class (`.up`, `.bt`, `.ta`, `.rd`, `.ms`…), so a modifier must carry its own prefix: `.vb-rowmenu-up` / `.vb-rowmenu-down`. Grep the prefix before naming anything new.
- **`components/MenuDotsIcon.jsx` is the shared ⋮ mark.** It had ALREADY drifted before this — `Scan.jsx` and `TutorProfileDetail.jsx` each declared their own copy and the two disagreed on `aria-hidden` — so a third copy was not on. `aria-hidden` is the correct half: every button it sits in already carries an `aria-label` naming the row.

### Navigation — six sections, not eleven links

The sidebar (`components/Layout.jsx`) is **Home · Learn · Explore · Tutor · Tools**, with **Settings** alone below the spacer. Nothing was added or removed in the move — every destination already had its own rail row; they are grouped now so the rail says what a learner can *do* rather than listing every screen at once.

- **No section has a landing page in front of it.** An `/explore` page holding Read and Podcast as two big cards was built and then **removed at the user's request** — a screen whose only job is to ask which of two things you meant is a click that buys nobody anything. `pages/Explore.jsx` / `Explore.css` and the `/explore` route are gone; don't reintroduce them. Keep Explore to Read and Podcast: a third item belongs there only when a third kind of content genuinely exists.

- **There is deliberately no `Practice` section** — the page is a stub. `/practice` is still routed but unreachable from the rail; a heading pointing at nothing is worse than no heading.
- **A section header is a `<button>`, not a link** — it opens the group rather than going anywhere, and a link that navigates nowhere lies to the keyboard and the screen reader alike.
- **In the collapsed rail, hovering a section shows a flyout** with its links — pure `:hover` / `:focus-within`, no animation, so it cannot be stranded by a tab that never composites. The flyout's `padding-left: calc(0.85rem + 10px)` is a **hover bridge, not spacing** — the nav item ends at the rail's *content* edge, so `left: 100%` leaves the rail's own padding uncovered and the panel would close as the pointer crossed it. Clicking a section in the rail expands the sidebar instead, since there is nowhere to draw the sub-list.
- Sub-items are **text only, tied to their parent by a tree line** (`.sb-sub` left border + a `::before` tick). A second column of glyphs would rebuild the clutter this removed — which is why the old per-feature icon components (`ScanIcon`, `ReadIcon`, `PodcastIcon`, `StudyIcon`, `ClassesIcon`, `BookingsIcon`, `MessagesIcon`, `FlashcardIcon`, `PracticeIcon`, `DashboardIcon`) came out of `Layout.jsx` with the flat list, and the "Study Area" heading with them.

### The streak flame — one drawn mark, two pages

`components/FlameMark.jsx`, used by the Dashboard hero badge (`.db-streak-flame`) and the Profile streak bar (`.pf-streak-mark`). It replaced `assets/dashboard/icon-streak.png`, which both pages already shared.

- **The reason for drawing it is NOT sharpness — it is that a raster cannot change colour.** The 512px PNG was already oversampled for a 17px mark. But both call sites needed a "no streak yet" state and both faked it the same way, with `filter: grayscale(1)`, which does not produce the app's grey: it produces a **desaturated orange**. As inline SVG the cold state is a real colour (`lit={false}`) and the two pages stop carrying two copies of a workaround.
- **The viewBox is `16 24`, not a square, and the box IS the proportion.** The reference illustration is a tall slender teardrop measuring roughly 0.65 wide to tall; the first attempt drew it on a 24 square and came out as a round blob with a dent in it. Both call sites therefore set width to **2/3 of height** (11.33/17 and 18.67/28) — the PNG era's rule, "height is set and width follows the square source", silently becomes wrong the moment the source stops being square.
- **`.db-streak-badge` went back to symmetric horizontal padding.** It carried `calc(1rem - 2.09px)` on the left because the PNG filled only 75.4% of its canvas (63px of transparent margin each side of 512), so the inset had to eat that margin for the flame to *look* 1rem in. The drawn mark runs edge to edge in its viewBox, so keeping the correction would have pushed the flame 2px **into** the padding. Measured after: left and right insets both 17.59px. **An ink-vs-box correction has to be re-derived whenever the artwork changes** — it is a property of the file, not of the layout.
- **The face and the sparks in the reference are deliberately not drawn.** This renders at 17px and 28px, where a mouth is three grey pixels and a spark is one. They belong to the illustration, not to the mark.
- Colours are **eyeballed from the supplied illustration, not sampled** — that file was never on disk. They are the mark's own rather than palette tokens: Verbo owns lavender and one salmon accent, and neither is a flame.
- `icon-streak.png` is now unreferenced but **kept on disk**, the same call as `icon-bell.png`: it is the supplied artwork and there is no other copy.

**It is ANIMATED, and it is the clearest worked example of what the frozen-compositor rule does and does not forbid** (`FlameMark.css`, prefix `fm-`). Six animations: a whole-mark float, an out-of-phase flicker on each of the two flame paths, and three rising embers.

- **The rule is not "no animation" — it is THE START POSITION MUST BE THE RESTING POSITION.** `rh-in` on the Read banner was transform-only and still had to be deleted, because a transform that never advances still *displaces*: it sat at `translateX(10px)` in a tab that was not drawing and left the text 11px off its padding. Every keyframe here begins and ends at `scale(1)`, no translation, no rotation, `opacity: 1`, so a tab that never composites renders exactly the static mark. Same construction as the practice assistant's typing dots.
- **HOW TO TEST THAT, because the obvious way is wrong.** Injecting `animation-play-state: paused` freezes each animation **at its current time**, not at zero — it does not rewind, so the reading is whatever phase the page happened to be in. That method was used once here and returned a clean all-identity result by luck, which is worse than failing. The deterministic test is the Web Animations API: `document.getAnimations().filter(a => a.animationName.startsWith('fm-')).forEach(a => { a.pause(); a.currentTime = 0 })`, then read `getComputedStyle`. Done that way all six elements report `matrix(1, 0, 0, 1, 0, 0)` and opacity 1. Seeking each to its own keyframe's peak instead is how the amplitudes were confirmed to be real.
- **Nothing here carries state.** Lit or cold is a FILL on the paths; the flicker says nothing a still frame does not, and the sparks only render when `lit`.
- **EVERY AMPLITUDE AND PERIOD WAS RAISED after the first pass read as barely moving** (*"make it better and noticable"*). The original was a 0.6-unit float over 3.4s under a 3% flicker — roughly half a pixel of travel at the badge's size, which is animated in the DOM and invisible on the screen. Now: float `-1.3` over 2.3s, outer flicker ±10% over 1.6s, inner ±13% over 1.15s, embers rising 3.4 units and shrinking to 0.55 at 8% opacity. **Fire also flickers fast** — a languid pulse reads as a loading state, so every period roughly halved.
- **The flame LEANS, and that is what stops it reading as a pulse.** Scale alone makes the shape breathe symmetrically, which at any amplitude looks like a thing being resized rather than burning. A ±2deg rotation sharing the same base origin makes the tip travel while the foot stays planted.
- **The badge mark grew 17px → 21px** (`width: 14px`, holding 2/3). At 17 an ember rendered about a pixel — present in the DOM, invisible on the screen. The pill absorbs the change because its height comes from the text's line box plus padding, not from the mark; measured 40.69px with 8.8px of headroom against the 6.74px a risen ember needs.
- **The embers are desynced BY DURATION (1.5s / 1.9s / 1.2s), NEVER by a negative `animation-delay`.** A negative delay starts an animation part-way through its timeline, so frame 0 stops being the resting position — it reintroduces the exact failure the rule exists to prevent, through a scheduling trick rather than a keyframe. Different periods drift apart on their own while all resting at 0%.
- **They rest VISIBLE and rise as they dim, rather than fading in from nothing.** A spark starting at `opacity: 0` would be missing entirely in a non-compositing tab. At rest the mark reads as the three sparks the reference shows in its own still frame, which is the right picture to be stuck on.
- **The embers are drawn at NEGATIVE `y`, outside the viewBox, painted by `overflow: visible`.** Growing the box upward to contain them would shrink the flame inside the same height and reintroduce the ink-is-not-the-box correction that dropping the PNG removed. **The rise is bounded by the padding above the mark, not by taste**: 3.4 units from a rest of -3.6 tops out at -7.0, which is 6.74px above the box at the badge's 21px and 8.2px at the Profile's 28px, against 8.8px and 12.31px of headroom. No ancestor clips at either call site. Raising the travel further means finding that padding first.
- Amounts are in the SVG's **own user units**, so the motion scales with the mark and needs no per-size tuning at 17px and 28px.
- `prefers-reduced-motion` removes the animations outright, which is safe precisely because every keyframe rests at the static position — there is nothing to strand.

**The Pro card at the foot of the rail** (`.sb-promo`) is a tag, a two-line pitch, the owl and one full-width CTA to `/upgrade`.

- **`assets/sidebar/owl-pro.png` is CROPPED TO ITS OWN INK, and that is the whole reason it can be positioned.** The supplied render was 577x433 with the bird occupying only the middle **215x336** — 63% of the frame was transparent padding, split unevenly 58/39 top to bottom. A `top`/`right` on that file positions the empty box, not the owl, which is exactly the "it will not align" symptom. Measured the alpha bounding box and cropped to it; the file barely shrank (120.2 → 119.2 KB, since transparent pixels compress to nothing), so this was never a weight optimisation. Kept at 215px for a ~66px slot — roughly 3x — deliberately: the logo section above records what a 1x raster looks like under this app's `zoom: 1.1`.
- **The owl sits INSIDE the card and cannot bleed past its edge.** `.sb-promo` is `overflow: hidden` because the collapse animates `max-height` to 0, so anything overlapping the top edge is clipped — the supplied mockup shows it poking out, and that cannot be reproduced without breaking the collapse. `.sb-promo-copy` reserves `padding-right: 74px` so the copy and the bird can never collide; measured 13.2px of clearance, zero overlap against the tag, title, text and button.
- **The card must stay under the collapse ceiling.** `.sb-user` / `.sb-promo` share `max-height: 240px` as the transition's stand-in for a measured height; the card is 169.7px, so there is headroom. A taller card would simply stop collapsing.
- **The CTA is dark on lavender, never white.** White on `#a89ce3` measures ~1.9:1; `#2b2643` on it is 5.6:1. Same rule the Read banner follows from the other side (white on the navy). The hover fill is not transitioned — the colour IS the feedback.
- **A light travels the CTA's border** (`sb-beam`), built to a supplied reference: a rotating conic-gradient `::before` under an inset `::after` that repaints the button's own fill, so only the 2px the fill does not cover is ever lit. The gradient is transparent for 250 of its 360 degrees and ramps to a white point at 342, which is what makes it a head with a tail rather than a rotating half-disc. **`inset: -75%`, not `-50%`** — the pseudo-element is a square being rotated, and at -50% its corners pull inside the button's corners four times a turn, so the beam blinks out at each one. The label needs its own `<span>` because `::after` paints over the button's own text. This does **not** break the frozen-compositor rule: nothing is transitioned and no state depends on the animation advancing, so a tab that never composites shows a finished, readable button with a static rim, and `prefers-reduced-motion` swaps the beam for a plain soft edge rather than stranding it mid-sweep.

### Notifications — raised inline, never scheduled

`notifications` (user_id, actor_id, type, title, body, link, read_at) via `Api\NotificationController`, with `components/NotificationMenu.jsx` (prefix `nm-`) as the bell + dropdown and `pages/Notifications.jsx` (prefix `nt-`) at `/notifications` as the All / Unread page. The bell sits immediately left of the account button in the Dashboard topbar.

- **This is the app's OWN table, not Laravel's notification system.** There is no queue, no mail driver and no notifiable trait here. **Do not run `php artisan notifications:table`** — it would try to create the same name with a completely different shape (uuid key, morphs, json payload).
- **`Notification::raise()`, not `push()`.** Eloquent already has a non-static `Model::push()`, and shadowing it with a static method is a fatal error — caught only because the first test run died on it.
- **`Notification::TYPES` is a closed whitelist**, and `raise()` throws on anything outside it. It also refuses to notify someone about their own action, which is the one rule every call site would otherwise have to remember for itself (a tutor confirming a lesson does not need telling they confirmed it).
- **Only events that actually happen in Verbo are built**: `booking_requested` (from `pay`, the moment a hold becomes a request waiting on the tutor), `booking_confirmed`, `booking_declined`, `booking_cancelled` (told to whichever side did *not* press the button), `message` (fans out to every live enrolment on a course thread), and `course_enrolled`. Quiz results, homework, course materials, vocabulary and study reminders were asked for but **not built — nothing in the app produces those events**, and a notification for an event that never fires is dead code.
- **Nothing here is time-based.** "Your lesson starts in an hour" needs a scheduler, and this app runs no cron or queue worker. Upcoming-lesson and course-starting-soon reminders are the one part of the design still missing, and they need `schedule:run` on a cron before they can exist.
- **Every notification carries a `link`** — a notification that is only information wastes the click. Clicking one navigates AND marks it read, so opening the thing it points at is what clears it. The read call is fire-and-forget: the badge is corrected locally first, and failing to record it must never block the navigation the user asked for.
- **Ordered by `created_at`, with `id` as the tiebreak** — that is what "newest" means, and it is the column the `(user_id, created_at)` index covers. Ordering by `id` alone looked right only because real rows agree; a backdated seed exposed it rendering oldest-first.
- `POST /notifications/read-all` must be declared **before** `/notifications/{notification}/read`, or `read-all` binds as an id — the same trap `bookings/clear-past` hit.
- The bell polls `/notifications/unread` once a minute, not the list. There are no websockets here, and a tight poll would burn the shared 300/min bucket for a number that is only ever a few minutes stale. **The badge shows presence, not a count** — a plain `#a89ce3` dot rather than a numeral: the exact number does not change what you do about it (you open the panel either way), and a numeral on a 42px button competes with the glyph for the same small space. The real count still reaches screen readers through the trigger's `aria-label`, which reads "Notifications, 2 unread" and drops back to plain "Notifications" at zero. The dot's ring is the page ground `#f9f8fe`, so it stays separate from the chip's edge instead of merging into it.
- **`destroy` is a real delete**, unlike hiding a booking: a notification belongs to exactly one person, so there is no second party whose record would be destroyed with it.
- **The bell is the Figma export (`assets/dashboard/icon-bell.png`), not a drawn icon** — it carries its own light chip and navy bell, so `.nm-trigger` is a transparent 42px hit area and the PNG is positioned inside it. The export pads its circle to **70% of the frame**, so the img is scaled to `143%` to make the visible chip exactly 42px; at 100% it renders ~29px and looks mismatched beside the account button. `pointer-events: none` on the img keeps clicks on the button. A baked raster cannot change colour, so hover/open is a `box-shadow` ring rather than a fill. **The bell and the account button both carry a deliberately slight lift** (`0 2px 6px` at 10-12%, rising to `0 4px 12px` on hover) so the pair reads as one raised control group — navy-tinted like every other shadow in the app rather than neutral black, which would grey the lavender under it. On the bell the ring and the lift must be **one shadow list**: a second `box-shadow` declaration replaces the first rather than adding to it, which would drop the ring the moment the lift was added. The file used is **`icon-bell-plain.png`**, a dot-free variant — the original export bakes in a lavender notification dot that could never turn off, so it claimed unread items at zero while the live red badge said none. Removing the dot alone was not enough: the artwork also **cuts 3-4px out of the bell's top-right to seat it**, which left the glyph looking bitten. The bell is provably symmetric everywhere else (from y=31 down its edges satisfy `L + R = 63` exactly), so the notched rows were rebuilt by mirroring its own left half about that axis — reconstruction, not guesswork, and all 17 rows now measure symmetric. `icon-bell.png` is untouched on disk. Replace `icon-bell-plain.png` if a clean dot-free export ever comes out of Figma.

Everything below the card is deliberately quiet now so the card can be the focal point — Chanel's rule, one accessory.

The dots moved inside it because they *are* the streak's evidence — the same fact drawn twice — so their own "LAST 7 DAYS" heading was one more equal-weight grey band on a page that already had five.

Verified at 2 / 12 / 365: the first two hold one row, 365 wraps to two rather than overflowing.

`pages/Settings.jsx` (prefix `se-`) at `/settings`, linked from the sidebar **below the spacer** rather than with the study content. Every control changes something real — there are no decorative toggles.

**Layout is a left sub-nav beside one panel**, rebuilt from three supplied references and combining two of them: ProDeel's left section list (Profile · Learning · Security · Appearance · Your data) with the CRM reference's row shape — label plus a line of help on the left, control on the right, hairline between rows. It replaced a 5-card grid, which is what made the page feel scattered: five cards, five save buttons, no single column for the eye to follow.

- **Duolingo's right-hand rail was deliberately NOT taken.** A second menu on the opposite edge from the app's own sidebar is the sprawl this redesign was asked to fix; navigation stays in one column.
- **ProDeel's read-only card + "Edit" button was not taken either.** It adds a mode to every field, and most of what is here is a toggle or a choice with no sensible "view" state.
- **There is deliberately no single Save button**, unlike the CRM reference: the name, password, picture and local preferences each hit a different endpoint at a different moment, and one batched save could not report a partial failure honestly. Same reasoning as `TutorEditDrawer`.
- **A section is a real address.** `?s=<key>` drives the panel (`useSearchParams`, `replace: true` so switching sections does not stack history entries), which is what lets the Profile page link straight at `/settings?s=security` instead of dropping someone at the top to hunt. An unknown `?s=` falls back to Profile rather than rendering nothing.

- The flash and error messages sit **above** the panel, not inside it, so switching section mid-read does not carry away the message about what you just did.

(Password reset does now send mail, so "this app sends no mail" is no longer the reason; the missing verification flow is.) `AuthContext` now exposes `setUser` so a rename updates the sidebar without a refetch.
- **Profile picture**: `users.avatar_path` + an appended `avatar_url` accessor, set by `POST /user/avatar` and cleared by `DELETE /user/avatar`. **Distinct from `tutor_profiles.photo_path`** on purpose — that is a tutor's marketing photo on Find Tutor, this is the personal avatar an account carries around the app, and most users are not tutors. Where both exist the account's own picture wins and the tutor photo is the fallback, so seeded tutors still show a face in a message row. `avatar_path` is deliberately **out of `$fillable`**: only the upload endpoint may move it, because that endpoint also owns deleting the replaced file — and it deletes the old one only *after* the new one is safely stored, so a failed write never leaves the account with no picture at all. Validated by **extension** (`mimes:`), not sniffed mimetype, the same trap podcast audio and chat attachments hit. The migration's `down()` deliberately **throws**: this machine's SQLite has no `ALTER TABLE DROP COLUMN`, so rolling back needs a raw-SQL table rebuild rather than a silent failure.
- **Picture editing lives here, next to the display name** — they are one thing (your identity) rather than two screens. The Profile page shows it and makes it the affordance: the avatar is a link to Settings with a "Change" label that appears only on hover, since an always-on label would sit on the user's own face every time they looked at their profile. - **Password**: `PUT /user/password` requires `current_password` even though the caller already holds a valid token — a token left on a shared machine is exactly the case this guards. On success every *other* token is revoked (the caller's own is spared, or you would be signed out of the tab you did it in).
- **Appearance**: the interface scale writes `--app-scale` (`src/appScale.js`, applied in `main.jsx` **before render** so the app never paints at the wrong size and then jumps). `--app-vh` is `calc(100vh / var(--app-scale))`, so the sidebar's height correction follows the scale automatically and needs no setting of its own — verified at 100/110/125%: the sidebar stays exactly viewport-height with zero phantom scroll at every step. `getAppScale()` only accepts values from `SCALE_OPTIONS`, so a hand-edited localStorage entry cannot render the app at 40x. The sidebar-collapse default writes the same `sb-collapsed` key the rail's own toggle uses.
- **Your data / sessions**: counts from `GET /user/stats`, and `POST /user/sessions/revoke-others` signs out every other device. It returns the count so the UI reports what actually happened rather than claiming success on a no-op.

### Emailed codes — confirming an address, and getting back in

One mechanism for two jobs: a six-digit code sent to an email address, used to confirm it after sign-up and to reset a forgotten password. `App\Models\EmailCode` + `App\Services\EmailCodeService` + `App\Notifications\EmailCodeNotification`, behind `Api\EmailVerificationController` and `Api\PasswordResetController`.

**A CODE RATHER THAN A LINK, and that is a real trade.** A link is longer and unguessable, but it only works in the browser that opens the mail — on a phone the app's session is in one browser and the link opens in the mail client's own, which is exactly where "it just takes me back to a login screen" comes from. A code is typed into the tab the person is already standing in. The guessability it costs is bought back by the attempt cap below. The earlier link implementation is gone, along with the `ResetPassword::createUrlUsing()` override in `AuthServiceProvider` and the `/reset-password/:token` page.

- **One table for both purposes**, because the mechanics are identical and two near-identical tables is how they would drift on expiry or attempt limits. `purpose` (`verify` | `reset`) keeps them from being one pool — a code issued to confirm an address must not be spendable on a password reset, and there is a test each way.
- **Keyed on the EMAIL, not a user id.** A reset code must be issuable for an address whose account we refuse to confirm exists, and matching on the string is what lets that endpoint answer identically either way.
- **The code is HASHED at rest** (`$hidden` on the model too). It grants a password reset, so it is a credential: storing it in the clear makes one database read into account takeover. `random_int`, never `rand()`/`mt_rand()`. A test asserts the digits are not the stored value, and another that they never appear in a response body.
- **THE ATTEMPT CAP IS WHAT MAKES SIX DIGITS SAFE** (`MAX_ATTEMPTS`, 5). A million possibilities sounds like plenty, but unlimited guessing falls in a weekend. After five wrong tries the row is consumed, so even the *right* code stops working and the attacker has to request another — which lands in the victim's inbox and is its own alarm.
- **Issuing invalidates every earlier code** for that address and purpose. Someone pressing "resend" would otherwise hold two live codes, which doubles the guessing surface and makes "the code did not work" depend on which email they happened to open.
- **Ten-minute expiry**, long enough to switch to a mail app and back, short enough that a code left on a shared screen stops mattering.
- **The answer is IDENTICAL for an unknown address**, and `reset` checks the code even when no such user exists — without that, a missing account returns measurably faster than a wrong code and hands back the very fact the endpoint hides.
- **Resetting revokes EVERY token** and rotates `remember_token`. Someone resetting has usually lost control of the password; leaving old sessions alive would mean the new password changes nothing for whoever already had one. It also **stamps `email_verified_at`** — receiving a code at that address proves the address, and nagging someone who just demonstrated they hold the mailbox would be silly.

**Sign-up runs `register → /verify-email → /onboarding → dashboard`.** `pages/VerifyEmail.jsx` is a real step, not a banner someone has to notice: registering has just emailed a code and that is the moment the person still has their inbox in mind, where landing on the dashboard means finding the email later, which is how an address goes unconfirmed forever. It is **inside `ProtectedRoute` but outside `Layout`**, exactly like Onboarding, and sits BEFORE it — confirming the address is about the account, onboarding is about preferences. `ProtectedRoute`'s onboarding redirect must therefore exempt `/verify-email` as well as `/onboarding`, or a brand-new account is bounced past the code straight to the questions. The page **sends no code on mount** — registration already sent one, and issuing another would invalidate it, so someone reading the first email while the page loaded would find that code rejected. Google sign-up goes to `/dashboard` instead and correctly: Google has proven the address, so `email_verified_at` is already stamped and the page bounces anyone verified back out.

**It still is not a GATE, though — there is a "Skip for now".** `components/VerifyEmailBanner.jsx` (prefix `ve-`) is mounted in `Layout` and keeps asking anyone who skipped. Registration returns a token regardless of whether the mail went out — blocking would mean one mail outage locks out every new sign-up at once, and this app runs no queue to retry a failed send with, so the failure would be total and silent. `AuthController::register` therefore does not check the send's return value; `EmailCodeService` has already logged whatever went wrong, and the banner offers a resend. Google sign-in already stamped `email_verified_at` (Google proved the address), so those accounts never see it. Dismissal is component state and `Layout` never unmounts, so it lasts the session and returns on the next load — anything longer would let someone permanently hide the one prompt that fixes the problem.

- **Mail is gated by `configured()`**, same as Stripe, Safe Browsing and Gemini: `log` and `array` are real drivers that "succeed" while sending nothing a person will ever see, so they do not count.
- **But the driver NAME is not enough, and this reached the UI once.** A configured-but-unreachable SMTP server sails past that check and throws from inside the transport, carrying the mail host, the port and PHP's socket internals — observed verbatim on screen as `Connection could not be established with host "mailpit:1025": stream_socket_client : php_network_getaddresses…`. `EmailCodeService::send()` catches it, logs the real reason for the operator and answers plainly, the same rule `ScanController` follows for the tesseract command line. There is a test asserting neither the host nor `stream_socket_client` appears in the response.
- **LOCALLY `MAIL_*` is Gmail SMTP**, and `MAIL_PASSWORD` is a Google **App Password**, never the account password — Google rejects the real one for SMTP, and an app password can be revoked on its own. `MAIL_FROM_ADDRESS` must equal `MAIL_USERNAME` or Gmail rewrites the sender. Paste it with the **spaces stripped**: Google displays it as four groups of four, and an unquoted space makes phpdotenv reject the ENTIRE `.env`, which takes the whole app down with "The environment file is invalid!", not just mail. `APP_NAME` was still `Laravel`, which is what the first test email was signed with; it is `Verbo` now, since `MAIL_FROM_NAME` interpolates it.
- **IN PRODUCTION IT IS `brevo`, BECAUSE RAILWAY BLOCKS EVERY OUTBOUND SMTP PORT.** Measured from inside the running container: 25, 465 and 587 to `smtp.gmail.com` all time out, `api.brevo.com:443` is open. It is an anti-spam policy, so no host/port/credential combination gets around it — Gmail SMTP works perfectly from a laptop and can never work from Railway. The symptom is a 503 from `/forgot-password` with `Connection timed out` in `storage/logs/laravel.log`; Railway's own log view will NOT show it, since Laravel logs to file on the volume rather than stdout.
  - `App\Mail\BrevoTransport` is a **Symfony transport**, registered with `Mail::extend('brevo', …)` in `AppServiceProvider`, not a direct API call at the one call site. That keeps `Notification`, the mail templates and every `Notification::fake()` test working untouched, and makes swapping provider a sibling class plus one env var.
  - **Brevo specifically** because it is the only free tier that sends to arbitrary recipients from a **single verified sender address** with no DNS domain ownership — Verbo has no domain, the site is a `vercel.app` subdomain. Resend and Mailgun both gate that behind domain verification and would only be able to email the owner. 300/day, no card.
  - **The Gmail API was considered and rejected on one fact**: it is HTTPS so it *would* clear the port block, but an OAuth consent screen in "Testing" issues refresh tokens that **expire after 7 days**, and lifting that needs either Google Workspace ("Internal") or full app verification with a security audit, because `gmail.send` is a restricted scope. A token that dies on a timer regardless of usage is not something to put behind a demo.
  - **`configured()` also requires the key when the driver is `brevo`**, so a keyless install says "this server cannot send email yet" rather than inviting someone to retry something that can never work.
  - **The timeout is short (10s) on purpose**: there is no queue, so the send happens inside the user's own request and a slow provider would otherwise hang a sign-up.
- **The code field is `type="text"` with `inputMode="numeric"`, never `type="number"`** — a number field strips leading zeros, and roughly one code in ten starts with one. The very first code generated in testing was `043651`, which is how this was caught rather than shipped.
- **The reset page is ONE route with two steps** (`/forgot-password`), not two. The code is typed back into the tab that asked for it, so a second route would invite a refresh or a back button between the halves and lose the address already entered. `ResetPassword.jsx` was deleted with the link flow.
- **`Login.jsx` renders a `notice` from router state.** Resetting navigates there with "Password changed. Sign in with it now." — before this the reset ended on a bare sign-in screen, which reads as "did that go through?" rather than as the success it was.
- **The Settings row exists because the change-password form above it cannot help the person who needs it.** That form requires the *current* password, which is precisely what someone signed in on a remembered device does not have. Every signed-in route here reads the address **off the session, never the request**, so none can be aimed at another account — there are tests posting someone else's email and asserting the code still goes to the caller.
- **THAT ROW SENDS *AND THEN NAVIGATES TO THE CODE FIELD*, and sending alone was a real bug.** It mailed a six-digit code and left the person in Settings holding it: they had to find `/forgot-password` themselves and retype the address they were already signed in as. Reported exactly that way — *"it email me, like, a code, and then I cannot use that code to do anything."* It now hands `{email, step: 'code', notice}` to that page through router state, which reads it once into `useState` so the fields stay editable and a reload still falls back to the normal first step. On failure it stays in Settings, so the error is read beside the button that caused it.
- **The button label names the wait.** Gmail's SMTP send happens inside the request and measures ~5s locally, which is long enough that a bare "Sending…" reads as stuck — it was screenshotted mid-send and reported as broken. It says "Emailing your code…" instead. (Production is Brevo over HTTPS and answers in ~1.5s.)
- Verified end to end against a throwaway local SMTP sink: register → code mailed → banner → wrong code refused → right code clears the banner; then forgot-password → code mailed → new password → redirected to sign-in with the notice → signed in with the new password. 29 tests.

### Read — admin-authored content with hover-translation

Modeled after the [Zhongwen popup dictionary](https://github.com/cschiller/zhongwen): admins publish articles/stories/fun facts (`articles` table: `title`, `type`, `body`, `body_en`, `image_path`, `user_id`), and any word in the body can be hovered for pinyin + English and saved to the flashcard bank with Alt+1 (`source_module: 'read'`).

- **Admin gating**: `users.is_admin` boolean (default false). No signup UI for it — promote an account manually via `php artisan tinker` (`User::where('email', '...')->update(['is_admin' => true])`). Enforced both server-side (`abort_unless($request->user()->is_admin, 403)` in `store`/`update`/`destroy`) and client-side (`{user?.is_admin && ...}` hides the create/edit/delete UI) — the server check is the real gate, the client one is just UX.
- **Hover-translation data comes from the same CEDICT index Scan already built** — no new dictionary or API. `DictionaryService::annotate()` (separate from `segment()`, used by Scan) tokenizes the *entire* body text, not just the Chinese words: Han-character runs become `{type: 'word', text, pinyin, translation}` tokens via longest-match against the index, everything else (whitespace, punctuation, English) passes through untouched as `{type: 'text', text}` tokens so the frontend can reproduce the original formatting exactly (rendered inside a `white-space: pre-wrap` block). `ArticleController::show` is the only place this runs — `index` returns lightweight rows without `body`/`tokens`, but it *does* fetch `body` internally to derive a 120-char `excerpt` for the card previews and then `unset()`s it before returning, so list payloads stay small while cards still have description text.
- **`body_en` powers the EN/CN toggle on the reader** (`articles.body_en`, nullable text). Chinese-only articles stay valid: when it's empty the EN button renders `disabled` with a "No English translation for this article yet" tooltip rather than showing a blank pane. CN is the default since the Chinese text is the actual learning content — it renders the annotated tokens with hover+Alt+1, while EN renders plain `body_en` with no tokenization. Both the create form (`Read.jsx`) and edit form (`ReadArticle.jsx`) expose it as an optional textarea.
- **Images**: uploaded to the `public` disk (`storage/app/public/articles/`), served via `php artisan storage:link` (already run — `backend/public/storage` is a symlink) and `Article::image_url` (an appended accessor, not a raw column). Editing with a new image deletes the old file first.
- **`APP_URL` must match the actual `php artisan serve` address** (`http://127.0.0.1:8000`, not the Laravel default `http://localhost`) — `Storage::disk('public')->url()` builds absolute URLs from it, and a mismatch means article images 404/connection-refused in the browser even though the API calls themselves work fine. Already fixed in `.env`/`.env.example`; don't reintroduce the default.
- Update uses `PUT /articles/{article}` with Laravel's `_method` form-spoofing field, since browsers can't send a real `multipart/form-data` PUT — the frontend (`api.updateArticle`) appends `_method=PUT` to the `FormData` and POSTs.

### Read — interactions, comments and recommendations

Built on top of the existing article/pinyin/translation reading system, not in place of it. Everything below was added with new migrations; `articles` keeps every original column and `type` (article/story/funfact) is untouched because the Read filter pills are built on it.

- **Pinyin and Translation are INDEPENDENT switches**, replacing the old single EN/CN swap. The Chinese never leaves the page — turning an aid on adds to it. Pinyin needed no new data: `DictionaryService::annotate()` already returns a `pinyin` on every word token, so the toggle just renders it above the character (`.rd-body-ruby` turns each word into a two-line inline-flex stack). The hover handlers stay on the outer `.rd-word`, so **Alt+1 flashcard saving still works with pinyin showing** — verified.
- **Per-sentence translation is NOT possible with the current data and was not faked.** `body_en` is one free-text block: the first article has 5 Chinese lines against 1 English line, and only 1 of 5 articles has any English at all. The translation renders as its own passage under the Chinese rather than pretending to be aligned line by line. Interleaving needs a per-sentence column, not more frontend code.
- **Reading time is DERIVED, never stored** (`Article::reading_minutes`): Han characters at ~300/min, everything else at ~200 words/min, floored at 1. A column would go stale the first time someone edited the body. It also handles a partial select — `index()` ships `LENGTH(body) AS body_length` instead of the body, and the accessor reads that when `body` is absent, or every card would report "1 min".
- **`index()` must use `select(...)`, never `get([...])`.** Passing columns to `get()` replaces the select list and drops `withCount`'s subselects with it — which silently shipped every full article body AND lost the `excerpt` the cards render from. Same trap `StudyLevelController::index` hit.
- **Likes and bookmarks are one row per pair, enforced by a unique index**, not by the controller — a double-tap racing itself hits the index and is simply already liked. Both are single toggle endpoints, and each returns the article's fresh counts plus that viewer's own state, so the button and the database cannot drift apart.
- **Comments allow exactly ONE level of replies.** Replying to a reply attaches to its top-level parent instead of nesting deeper (`$parentId = $parent->parent_id ?: $parent->id`), so the thread stays readable and the client needs no recursion. Verified: a reply-to-a-reply landed on the top-level comment. The author may edit or delete their own; an admin may delete any, which is the only moderation path.
- **`article_views` is one row per user per article with a counter**, not an append-only log: the recommender only asks "has this person read things like this", and a log would grow without bound for an answer that never needs more than the latest visit.
- **Shares are recorded but deliberately excluded from recommendation scoring** — sharing an article with a friend says nothing about whether *you* want more like it. The share sheet offers copy-link, the device's own share sheet where one exists, and Telegram/Facebook/X. No social system was built.
- **Recommendations are rule-based and self-explaining.** `RecommendationService::POINTS` holds the weights in one place (hsk 2, goal 3, focus 2, interest 2, style 1, liked-similar 2, bookmarked-similar 2). Points and reasons are produced together, so the sentence can never claim something the score did not count. **The reverse does NOT hold, deliberately**: a point may be scored without adding a clause where that clause would only repeat one already said — liking AND saving things with the same tag is one reason, and a stated format preference plus the behaviour matching it is one fact said twice.

**The wording is per TAG KIND, not one template.** `article_tags` holds four kinds (goal, focus, interest, style) and "about {value}" is right for a topic and wrong for the rest. Flattening them — matching on `value` while ignoring `kind` — is what produced **"you saved other articles about Articles"**, which is a `style` tag read as a subject. The engaged-tag set is keyed `kind|value` now, so a `style` match cannot be described as a topic and a value shared by two kinds ("Travel" is both a goal and an interest here) stays two different facts. Similarity clauses: interest "about X", focus "on X", goal "for X", style "in the same format" — which names no subject, because a format has none. Preference clauses: "it fits your X goal", "you're working on X", "you're interested in X", "you prefer X"; the old single template read "it matches your preferred format in Articles".

Already-read articles are pushed down, not hidden — re-reading is legitimate, but it should not crowd out new material. Ties break on unread-first, then newest, so equal scores do not order themselves by database id.
- **Learning preferences live in their own table**, not on `users`: four multi-selects plus two single values that most of the app never reads, and keeping them out of `users` keeps them off every auth payload. The option lists live on the `LearningPreference` model and ride along in the `GET` response, so the settings UI never carries its own copy — a hard-coded list in the client is how it drifts from what the validator accepts.
- `GET /articles/recommended` must be declared **before** `/articles/{article}`, or "recommended" binds as an id — the same trap `bookings/clear-past` and `notifications/read-all` hit.
- **Metadata chips are deduped by value.** An article tagged "Travel" as both a goal and an interest is one idea to the reader; two identical chips just look like a mistake. Anything already said by the category or difficulty chip is dropped too.
- **The like and comment marks are shared inline SVG** (`components/ArticleIcons.jsx`), used by both the action bar and the list cards so the same idea is never drawn two ways. They replaced a text `♥` beside a colour emoji `💬`, which mixed a font glyph with an emoji — the two disagreed on weight, size and colour, and neither could follow `currentColor`. All four are on a 24 grid at `strokeWidth 1.7`, rendered 17px in the action bar and 14px on a card; `filled` swaps outline for solid, which is what carries the liked state.
- The list cards show counts but **no like/save buttons** — the card is for choosing what to read, and liking from there would mean reacting to something you have not read yet.

### Tutor verification — apply, review, approve

**Becoming a tutor is an APPLICATION, not a form that publishes you.** `POST /tutor-profile` used to create a live, publicly listed tutor in one click; it now lodges an application at `status: pending`, and nothing lists it until an admin approves. Flow: apply (`pages/BecomeTutor.jsx`, prefix `bt-`, at `/become-a-tutor`) → admin review (`pages/TutorApplications.jsx`, prefix `ta-`, at `/tutor-applications`) → approve / reject / request more info → the profile appears in Find Tutor.

- **Status lives ON `tutor_profiles`, not in a separate applications table.** The application IS the profile. A separate table would mean copying every field across on approval and holding two answers to "what does this tutor teach" — one being reviewed and one being shown — which is exactly how the two drift. Reviewing the row that will be published means the admin approves what students actually see.
- **EXISTING TUTORS WERE GRANDFATHERED TO `approved` IN THE MIGRATION, and that is not a convenience.** The alternative is destructive: those four profiles are already listed, already hold live bookings and already have message threads, so defaulting them to `pending` would delist all of them at once and leave students with confirmed lessons pointing at a tutor who appears not to exist. Same decision as stamping `users.onboarded_at` for accounts that predate onboarding. Their `submitted_at`/`reviewed_at` stay **null** — nobody applied and nobody reviewed, and writing a timestamp would invent a review that never happened; the queue reads `pending`/`needs_info`, so they never appear in it. `decide()` refuses them with a 409 for the same reason.
- **`TutorProfile::scopeApproved()` is what keeps an unreviewed tutor out of the marketplace**, and it is a scope precisely so no listing can forget it. **Filtering the list is not enough**: `showProfile` takes an id, so an unapproved profile stays readable to anyone holding the URL — it 404s for everyone but the applicant and an admin. 404 rather than 403, because a 403 confirms that this particular person applied, which is theirs to disclose.
- **`status`, `submitted_at`, `reviewed_at`, `reviewed_by` and `review_note` are deliberately NOT `$fillable`** — an applicant must not be able to post their own approval. That means mass assignment DROPS them, so they are set with `forceFill` after the upsert. Putting them in the `$data` array left every application at `status: null`, which four tests caught. Same trap as setting a non-fillable foreign key through `updateOrCreate`.
- **An approved tutor cannot be pushed back into the queue by reapplying** (409). Editing a published profile is the drawer on the profile page; resubmitting would delist a live tutor mid-term with real bookings against them. The guard **queries** rather than reading `$request->user()->tutorProfile`, because that cached relation answers from memory once anything has touched it — a check that can silently read the wrong value is not a check.
- **`needs_info` is a real state, not a rejection with a note.** A rejection is a decision; "add your certificate and resubmit" is a conversation still open, and collapsing them tells someone they failed when they were only asked a question. Rejecting and requesting info both **require** a note — "no" without a reason is not something an applicant can act on. Resubmission is the same `store` endpoint and clears the previous decision, so a stale note cannot contradict the new state.
- **Evidence (`tutor_credentials`) is on the PRIVATE disk** and streamed through a route that re-checks the caller — a certificate carries a real name and often a date of birth. The model deliberately has **no `url` accessor**, unlike `photo_url`/`image_url`, so it cannot be handed to a browser by a careless `->toArray()`; `path` is not fillable and is never serialised. The admin's document links fetch a blob with the bearer token, the same way `MessageAttachment` does, because an `<a href>` cannot send one. Uploads happen immediately rather than on submit: an application can be resubmitted several times and re-uploading the same certificate each round is busywork.
- **`GET /tutor-profile` returns `{profile, options}`, NOT the profile.** `options` carries the validator's own lists so the form cannot drift from what the server accepts (same reason `LearningPreference` ships its). This shape change broke two existing callers and one badly: `Bookings.jsx` tested `Boolean(profile)` for the teacher switch, and the wrapper is always truthy, so **every account would have seen it**. It reads `mine?.profile?.status === 'approved'` now — a pending applicant is not a tutor, and a teacher view with nothing in it is worse than no switch.
- The admin page is gated in the client too, but **the server is the real gate** — every endpoint checks `is_admin`. The nav item is filtered once from a derived list rather than at each of the five places `NAV` renders: an item that must be hidden in five spots eventually shows up in one.
- **Nothing in this app ships the browser's own `Choose File / No file chosen`.** Every upload anywhere — the edit drawers (`.ed-btn-ghost`), a study level (`.sl-btn-quiet`), Settings, Messages, Scan — is a **hidden `input[type=file]` behind a styled control**, and the apply form shipped two raw ones. They are `.bt-btn-ghost` now, the same box as `.ed-btn-ghost`. Watch the trap that forced the markup change: the `Field` helper is a `<label>`, so the photo picker (also a label) cannot sit inside it — labels do not nest, and the click breaks. The photo block is a plain `div.bt-photo-field` for that reason.
- **The application's photo goes through `ImageCropper` like every other photo in the app**, at the component's default **13:15 — the 130x150 `.ft-card-photo` box on Find Tutor**, which is where the photo actually lands. Its own thumbnail is that shape at 60% (78x90), so the frame the applicant crops to is the frame students see. Note `TutorEditDrawer` crops the *same column* at `aspect={1}` because its preview is a 74px circle; the two disagree, and the drawer is the odd one out. Left alone rather than changed blind — square art still fills the card via `object-fit: cover`, just cropped tighter at the sides.
- **The section headings are floated legends, not notched ones.** `.bt-group` is a `<fieldset>` because these are genuinely groups of controls, but a fieldset cuts its own top border to seat the legend and **no other card in the app breaks its outline for a heading**. `float: left; width: 100%` takes the legend out of "rendered legend" status so it lays out as an ordinary block inside the card (`legend + * { clear: left }` stops the two overlapping). The fieldset also needs **`min-inline-size: 0`** — the UA sheet gives it `min-content`, which no `width` overrides and which would stop the card shrinking with the rest of the page.
- Verified end to end: 11 tests, plus in the browser — the four grandfathered tutors still list, the apply form renders its server-supplied options, the queue shows "Approved 4", and a non-admin sees no Applications link and is redirected off the page.

- **Styled areas so far: the sidebar shell, Dashboard, Find Tutor, Scan, Read (list + article), Login and Register.** Each has its own stylesheet with a unique class prefix — `Layout.css`/`sb-`, `Dashboard.css`/`db-`, `FindTutor.css`/`ft-`, `Scan.css`/`sc-`, `ScanDocument.css`/`sd-`, `Read.css`/`rd-` (shared by `Read.jsx` and `ReadArticle.jsx`), `Login.css`/`lg-`, `Register.css`/`su-`. **Sign-in wears the same shell as sign-up** — the shared dark gradient panel with the feather, not the radial gradients and centred graduate illustration it used to have; 14 computed properties were compared across the two pages and none differ. - **`getBoundingClientRect()` and CSS lengths inside `#root` are DIFFERENT UNITS.** `#root` carries `zoom: var(--app-scale)`, so a rect measured from the viewport is already multiplied by the scale, while a `top`/`left` written onto an element inside `#root` gets multiplied by it *again*. `WordPopover` mixed the two and rendered ~67px below and ~69px right of the word it points at — at 1.1, an intended `top: 670.8` painted at 737.9, past the word's own top edge. **Three CSS traps that bit repeatedly across the narrow-width work**, all worth checking before reaching for a new breakpoint:

1. **A flex item defaults to `min-width: auto`** — its min-content width — so a card whose content is wider than its `flex-basis` simply ignores the basis. `min-width: 0` is what makes a width mean anything. This is documented for `.db-pickup > *` and hit again on `.db-grid3 > *`.
2. **`box-sizing: border-box` is not universal here.** `.db-teacher` lacked it while `.db-pod` had it, so given the same basis it rendered 272.9px against 250.9 — 20px padding plus 2px border added on top — and every section edge below it sat 22px further right.
3. **A percentage size on an absolutely positioned decoration creates a loop.** The study carousel's book was `height: 96%` of a stage whose height tracks the text, so its width could not be stated as a number and the fan clipped by 58.8px a side. Pin the decoration and size it against its container instead (`width: min(250px, 33%)`), and centre with `inset: 0; margin: auto` rather than a hand-written negative margin, which cannot survive a fluid width.

**The type settings come from the Figma inspector, not from the pixels: Etna, size 20, letter spacing 0%, plus the font's own kerning.** On a 1000-unit em that is scale `0.02`, giving ink of **52.02 x 13.98 at (60.50, 13.05)** — and the export's measured box is 52 x 14, so both dimensions agree to within 0.1%.

**Kerning is the part that is easy to miss and it is load-bearing.** Etna has no legacy `kern` table; its pairs live in **GPOS, lookup type 2** (`kern.js` in the scratchpad parses PairPos formats 1 and 2, with Coverage and ClassDef). "Verbo" has exactly **one** kerned pair — `Ve` at **-159 units (-3.18px at 20px)** — and it is the difference between the unkerned ink (55.20px) and the real one (52.02px). Omitting it is visible to the naked eye as a gap after the V, which is how it was caught. Kerning is also **not** letter spacing: Figma reports 0% spacing and applies the feature on top, so reading "0%" as "use raw advance widths" is the trap.

**Do not re-derive the size by fitting the raster** — three attempts did and all three were wrong. Anchoring on a bounding-box dimension fails because 52 wide and 14 tall are integer counts off a soft export that disagree by 6% at Etna's *unkerned* metrics. Fitting scale by minimising difference against the original is biased small, because a resampled original never reaches the peak ink of the true shape; it came back ~8% short. And giving that fit a free tracking parameter produced a confident `-0.040em` — which is simply the one real `Ve` kern pair smeared evenly across all four gaps, right in total and wrong everywhere. Error per channel over the word region tells the story: 20.31 fitted with free tracking, 17.16 fitted scale-only, 16.70 at the design's size unkerned, **6.84 kerned**. Whole-logo mean difference against the original is **1.99/255**.

All three enforce the same rule Verbo does — a lesson fits inside ONE opening — and all three allow several openings a day, which Verbo already allowed. What they all do differently is make you handle a thing with two ends, so the length is in front of you.

  **The rewrite DELETED code rather than adding it**, because `tutor_availability` already stores `start_time`/`end_time`: `rangesToChips`, `chipsToRanges`, the half-hour snapping, the "we trimmed your hours" warning, `PART_BANDS` and the whole chip stylesheet are gone. The editor's state is now `{day: [{start, end}]}` — the same shape the table holds.
  - **The invalid-range property is preserved, deliberately.** The "to" list only offers times later than the "from", and moving the "from" past the "to" drags the "to" with it, so a backwards range still cannot be expressed rather than being something the teacher is told off about afterwards.
  - **Off-grid rows are offered as their own option, never snapped.** `timeChoices(current)` appends a saved value that is not on the half hour instead of moving it inward, which is why the snap warning could be deleted — the tutor's real hours round-trip untouched.
  - **Choices are half hours, not Google's quarter hours**, matching `SlotService::STEP_MINUTES`: a 6:45 opening would generate starts off the grid every other tutor's times land on.
  - **Overlapping rows merge on save** (`mergeRanges`), so `9–10` plus `9:30–11` stores as one `9–11` rather than two rows offering the same times twice. The UI re-seeds from the save response, so the merge is visible immediately rather than being a silent rewrite.
  - `hhmm()` trims `"09:00:00"` to `"09:00"` — Postgres returns a `time` column with seconds while SQLite hands back the string it was given, and both have to select the same `<option>`.
- **`24:00` IS A VALID `end_time` and the validator must keep accepting it.** Ticking the last chip of a day (23:30) closes a range at midnight, so the editor sends `24:00` — and `date_format:H:i` rejects it, because `H` is 00-23. Since the save is a **wholesale replace**, that one row took the tutor's entire week with it: the response was a 422 reading `slots.1.end_time does not match the format H:i` (an array index naming no day), nothing was written, and the hours therefore looked unchanged after a reload — reported as "I set Wednesday but it doesn't show, even if I refresh". `end_time` is validated by regex now (`00:00`-`23:59`, plus `24:00`) with messages that describe the window instead of its index. `24:00` is a real boundary rather than a workaround: **PostgreSQL's `time` accepts it as its documented maximum**, `Carbon::setTime(24, 0)` rolls to the next midnight, and `SlotService` already splits on `:` and so reads it correctly — verified generating 22:00 / 22:30 / 23:00 / 23:30. `after:` still guards the ordering, because `strtotime('24:00')` resolves to the following midnight. `tests/Feature/TutorAvailabilityTest.php` covers it, including that a rejected row must not wipe the week.
- **Weekly hours are set in the edit drawer's `Hours` tab** — `TutorEditDrawer`, loaded lazily since most edit sessions never open it and the profile payload does not carry the rows. The week is held whole and posted in one call because `TutorAvailabilityController::store` is a wholesale replace. **Do not confuse it with `tutor_profiles.availability`**, the free-text line on the Profile tab ("9am-12pm"): that is descriptive only, feeds the Find Tutor filter, and creates **no bookable slots whatsoever** — the tab carries a note saying so, because the two being one word apart is exactly how someone fills in the wrong one and wonders why nobody can book them. The timezone selector lives here too and defaults to the browser's zone; it is what the wall-clock hours mean. An end-before-start range is caught client-side as well as server-side so the message names the day rather than arriving as `slots.2.end_time must be after slots.2.start_time`.
- **Booking is a scheduled trial class, not a contact request.** A tutor's bookable times come from `tutor_availability` (weekly recurring `day_of_week` + `start_time`/`end_time`), and `SlotService` turns those into concrete datetimes **on read** — weekly hours are the source of truth, so editing them takes effect immediately and there is no slot table to run dry. Times in that table are **wall-clock in the tutor's own timezone** (`tutor_profiles.timezone`), not UTC: a recurring "9am" must stay 9am for them across a DST change. `bookings.starts_at` is UTC.
- **`BookingDialog` is laid out from `design/book a trail/book a trail.png`**, measured not eyeballed: a 331x577 card in **three bands** — white header, `#fcfcff` body, `#f9f8fe` footer — 25px content padding, a paging 7-day strip, times split into **Morning / Afternoon / Evening**, and a full-width CTA. Empty days stay in the strip greyed rather than being dropped: an empty Tuesday is information, and hiding it makes the calendar look shorter than it is. The initial day must be re-picked whenever the week changes, **not only when the selection falls outside it** — on first render the slots have not arrived, every day looks empty, and today gets chosen, which is often the one day with nothing left on it. The optional message field is not in the mockup (which simply did not depict it) so it is folded behind a `+ Add a message` link, leaving the default view matching the design exactly.
- **Booking happens in `components/BookingDialog.jsx` (prefix `bk-`)**, opened from both the preview card on `FindTutor` and the buttons on `TutorProfileDetail`. It has to exist: `starts_at` is required by `BookingController::store`, and neither page has a picker, so before it the booking buttons just 422'd. The scrim carries a static `backdrop-filter: blur(7px)` — **never transitioned**, for the same reason the quiz verdict colour is not: a transition only advances while the tab gets frames, so a stalled one would leave the page behind half-blurred. Mounting blurs, unmounting restores, with no in-between state to strand in. Times are grouped by the **student's** local date, not the tutor's `day` field — a late slot in the tutor's evening can fall on the next day for the student, and filing it under the tutor's heading would put it on the wrong tab. A 409 (someone took the slot first) refetches the list rather than leaving a dead time on offer. The hold countdown uses `setInterval`, not `requestAnimationFrame`, since rAF is throttled to nothing in a background tab — exactly when a 15-minute hold is most likely to lapse unwatched.
- **The separate "send a message" request is gone.** A message is now an optional field on a booking rather than a request of its own, so there is one flow instead of two that meant different things; `TutorProfileDetail`'s inline form and `.td-message-form` were removed, and both its buttons open the dialog. The button reads **"Trial booked"** once live, on both pages — it used to say "Request sent" on one and nothing consistent on the other.
- **Group courses are the second product, and deliberately the opposite shape.** `courses` (tutor_profile_id, title, level, outcomes, price, weeks, total_classes, classes_per_week, minutes_per_class, capacity, starts_on/ends_on, `days_of_week` json, start_time/end_time) + `course_enrollments` (course_id, user_id, status, hold_expires_at, **unique on the pair**) via `Api\CourseController`. Courses are authored in the edit drawer's **Courses** tab, loaded lazily like the weekly hours; its weekday picker reuses the Hours tab's 0=Sunday numbering. A private lesson is a length the student schedules; a course is a fixed run of dates they accept — so **none of this touches `tutor_availability` or `SlotService`, and `CourseDetail` shows no calendar at all**. `price` is for the whole run, which is why the card reads "$80 total" and the secondary line is `8 weeks · 16 classes · 60 min/class · 6/10 students` rather than a duration, which means nothing for something sold by the term. Seats are counted from `liveEnrollments` (held or confirmed) so a cancellation frees one; capacity is re-checked **inside** the enrol transaction, since two people can pass a check outside it and both take the last seat.
- **`pages/Checkout.jsx` (prefix `ck-`) at `/checkout/:kind/:id` is shared by both flows** — `kind` is `lesson` or `course`. The two differ entirely up to this point and are identical after it (summary → payment → confirmation), so they share one page rather than two that drift apart. **Payment is a mock**: there is no Stripe key in the repo, so nothing is charged and no card details are collected — the page says so on screen rather than mocking up a card form, and the Pay button calls the existing `confirm` endpoints, which are the seam a real webhook replaces. `BookingDialog` no longer settles a booking itself; it creates the hold and navigates here.
- **The tutor's price list is `components/TutorLessonsCard.jsx` (prefix `tl-`)**, built from a user-supplied reference: deep `#6a6191` rows carrying an `#a89ce3` price pill, behind a **Private Lessons / Group Courses** toggle, paged three at a time with a dot strip. Courses are fetched lazily the first time the group tab is opened — they are not in the profile payload and most visitors never look.
- **Paying is NOT accepting, and conflating them was a real bug.** The checkout screen once called `confirm`, so a lesson read "Confirmed" the moment the student paid and the tutor never saw a request at all. The chain is now `held → pending → confirmed`: **`POST /bookings/{booking}/pay`** (student-only) turns the hold into a paid **request** and clears `hold_expires_at` — it is paid, so it no longer lapses, it waits on the tutor — and **`POST /bookings/{booking}/confirm` is tutor-only**, which is what actually confirms it. A student calling confirm gets a 403. Group enrolments still settle at payment, because a course has no approval step: the tutor published the schedule and seats are seats.
- **`pending` had to be added to the slot predicate in two places** — the partial unique index and `SlotService`'s taken set. A paid request that did not occupy its slot would let someone else book the same time while the first student waited on the tutor.
- **A new booking is a *hold*, not a confirmation.** `status` runs `held → confirmed | cancelled | expired`, with `hold_expires_at` at +15 min. `POST /bookings/{booking}/confirm` is the seam **Stripe plugs into** — today it is called directly, later by the payment webhook; nothing else needs to change.
- **Three things guard a slot, and all three are needed.** `store` rejects any `starts_at` the tutor does not actually offer (a client could otherwise post any datetime and book outside their hours); it releases lapsed holds on that slot inside the transaction; and a **partial unique index** `bookings(tutor_id, starts_at) WHERE status IN ('held','confirmed')` is the last word when two students race — one insert wins, the other gets a 409. The index is partial precisely so cancelling or expiring frees the time by flipping status *out of the predicate*, with no cleanup job. Written in raw SQL because Laravel 9's schema builder has no partial-index helper.
- **`confirm` must check `status === 'held'`, not just expiry.** Once another booking takes the slot this row is already flipped to `expired`, so an expiry-only check falls through, hits the unique index, and leaks raw SQL to the client. Both that status check and a `QueryException` catch are in place.
- **Bookings are a simple request record, not a scheduler**: `bookings` table (`student_id`, `tutor_id`, `message`, `status` default `pending`) — no date/time slots, no accept/reject action yet, just a contact request a student sends a tutor. `BookingController::index` returns both directions in one call, `{sent, received}`, since any user can be both a student and a tutor simultaneously.
- **"Request sent" is driven by *live* bookings only** — `src/bookings.js` (`isBookingLive` / `hasLiveBookingWith`) is the single rule, used by both `TutorProfileDetail` and `FindTutor`. `cancelled` and `expired` do not count, and a `held` row past its `hold_expires_at` does not either (mirroring `Booking::getIsExpiredAttribute()`, which is an accessor and is *not* appended to the JSON). Before this, the detail page asked only "does a booking to this tutor exist", so cancelling one left the button reading "Request sent" and disabled forever with no way back. `FindTutor` had the mirror-image bug: its `bookingSentTo` was its own state that only filled in after booking within the session, so a reload lost the badge — it is now derived from `bookings.sent`, which is the one source of truth for both pages.
- **Find Tutor no longer edits or lists bookings.** The two unstyled `<li>` booking lists and the "Edit my tutor profile" block were removed from the bottom of the page: reviewing bookings is `/bookings`, and editing a profile is the drawer on that profile's own page, so each job has exactly one home. **The create path stayed** — "Become a tutor" is the only way to make a profile in the first place, so the block now renders only when the user has none. An existing tutor reaches their own profile by clicking their own card, which reads "This is your profile" and links to `/find-tutor/{id}`. Removing those sections orphaned `profileSaved` and four `ft-` rules (`ft-bookings-list`, `ft-booking-row`, `ft-booking-status`, `ft-saved-note`), all deleted.
- **`pages/Bookings.jsx` (prefix `bo-`) at `/bookings` is a booking dashboard organised by STATE, not by direction.** Three tabs — Upcoming / Requests / Past — and **the order flips by role**: a student opens it asking "is my lesson confirmed?", a tutor asking "what is waiting on me?", so the teacher view leads with Requests. Switching role lands on that role's first tab, otherwise reordering them achieves nothing. The role switch only appears for an account that actually has a tutor profile.
- **One status vocabulary, five words**: Pending / Confirmed / Declined / Completed / Cancelled. `held` and `pending` both collapse to **Pending** (the tutor has not answered), and **`completed` is derived, not stored** — a confirmed lesson whose end time has passed is finished, so no job has to sweep the table to keep it true. `endsAt()` is used rather than `starts_at` so a lesson stays Upcoming while it is actually running.
- **`bookings.cancelled_by` records which side called a confirmed lesson off** ('tutor' or 'student'), with the reason reused from `decline_reason`. Without it the student saw the same plain "Cancelled" whether they cancelled or the tutor cancelled on them — and only the second should offer them another time. The row now reads "Lin Wanqing cancelled this lesson. Something came up on my side." with a **Find another time** action.
- **Clearing a row from Past hides it for ONE side; it is never a delete.** `bookings.hidden_for_student_at` / `hidden_for_tutor_at` and `course_enrollments.hidden_at`, filtered with `whereNull` in `index()` / `myEnrollments()`. The row belongs to both people: a student tidying their history must not erase the tutor's record of a lesson that happened — verified, a booking the student removed is still on the tutor's list. **`POST /bookings/clear-past`** empties the whole list in one call rather than one request per row against the shared 300/min bucket; it is scoped by `role` because that is what the tab shows, and it skips live rows by the same rule. Its route must be declared **before** `DELETE /bookings/{booking}` or `clear-past` binds as an id. The button arms on the first click and acts on the second (the pattern Scan's delete uses), disarming on a 4s timer rather than on blur, and says plainly that it only clears your own list. `DELETE /bookings/{booking}` **refuses while the booking is still live** (`held`/`pending`/`confirmed` and not expired) with "Cancel this booking before clearing it from your list", because hiding a lesson someone is still expecting would silently lose it.
- **`declined` is a distinct status from `cancelled`**, with a `bookings.decline_reason`. The student must be able to tell "you called this off" from "the tutor was not available" — only the second offers them another time. `POST /bookings/{booking}/decline` is tutor-only and asks for a reason; declining frees the slot the same way cancelling does, since `declined` sits outside both the partial unique index and `SlotService`'s taken set.
- **Group courses never enter the request flow.** The tutor published the schedule, so enrolment is immediate — enrolments only ever appear as Upcoming or Past, never under Requests. Private is `Request → tutor confirms → Booking`; group is `Enroll → Payment → Confirmed`.
- **`GET /tutors/{profile}/slots` returns `has_availability`.** An empty slot list has two very different causes — the tutor published no weekly hours at all, or they have hours but nothing fits this lesson — and the list alone cannot distinguish them. Without the flag the dialog told people to "try a shorter lesson" for a tutor who had set no hours whatsoever.
- **It returns `longest_window_minutes` too, because there is a THIRD empty case and it was being read as a broken calendar.** A booking must sit inside ONE unbroken window, so a 60-minute lesson cannot fit a 30-minute opening — a tutor who ticks scattered single chips makes their own long lesson unbookable on **every day at once**, while the 30-minute lessons beside it book fine. The dialog said only "No free 60-minute slots on this day", which is true of the day, hides the fact that no day will ever work, and invites paging through a fortnight. Reported exactly that way: "in trial it works… but the HSK 3 exam practice has no available option". Now, when the whole list is empty **and** the longest window is shorter than the lesson, it says so and offers the lessons that do fit as buttons that switch to them. The value is derived from the rows, never stored. Guard on `slots.length === 0` as well as the measurement — a long-enough window that is simply fully booked is a different fact and keeps the per-day message.
- **The Hours tab warns the tutor at the source**, which is where this is actually fixable: `longestBlockMinutes` is the longest single row in the week, and any lesson longer than it is named as unbookable — "Your longest single opening is 30m, so HSK 3 Exam Practice (1h) is not bookable". Computed off the editor's live state rather than the saved rows, so it answers while they edit and clears the moment the opening is made long enough — verified both ways. **Said in lengths, never in the word "block"**: the first wording read "your longest unbroken block is 30 minutes", which is the app's vocabulary and not a teacher's.
- **`BookingController::index` does not filter by status**, so cancelled bookings still appear in the sent/received lists. That is deliberate — "you cancelled this" is more useful to a student than a row that silently vanishes.
- A user cannot book themselves — enforced server-side in `BookingController::store` (`tutor_id === $request->user()->id` check), not just hidden client-side.
- Same string/int FK gotcha as elsewhere: `tutor_profiles.user_id` and `bookings.student_id`/`tutor_id` come back as strings from SQLite on list endpoints, so the frontend coerces with `Number(...)` before comparing against `user.id` (e.g. to detect "this is your own profile" or dedupe your profile out of a stale list).

### Tutor portal — classrooms, curriculum and submissions

`classrooms` + `classroom_members` + `classroom_items` + `submissions` (and a file table for each) via `Api\ClassroomController` and `Api\ClassroomItemController`, with `pages/Classes.jsx` (the hub) and `pages/Classroom.jsx` (one class), prefix `cl-`. Reached from the **Classes** item in the sidebar, sitting with Bookings and Messages — the things you do with other people, rather than the solo study tools above it.

- **CREATING A CLASS NEEDS AN APPROVED TUTOR PROFILE, OR `is_admin`.** It used to need nothing but an account, so the Classes page offered a student a "Create class" button — reported exactly that way. `ClassroomController::canTeach()` asks `TutorProfile::scopeApproved()` rather than testing `status` inline, so there is one definition of "is a tutor" in the app, and a pending applicant is not one (the lesson `Bookings.jsx` already had to learn). A classroom holds real students, a join code and their submitted work; letting any account conjure one skips the verification the marketplace insists on before someone may present as a teacher. **`store` is the gate and the check runs BEFORE validation**, so a student posting straight at the endpoint gets a plain 403 rather than being told which fields they got wrong. Nothing needed grandfathering — every existing classroom was already owned by an approved tutor, checked before this landed; if that ever stops being true, gate CREATION only, because an existing class must keep working for the students inside it.
- **`index()` ships `can_teach`, and it is a MIRROR of that rule rather than the rule.** It rides on the payload the page already fetches instead of costing it a second call to `GET /tutor-profile` — the same reasoning as `has_availability` on the slots response. The client defaults it to **false** until the server answers: a create card that appears for an instant and is then taken away is worse than one that arrives a moment late. The page also swaps its subtitle and its empty state, so it never promises teaching to an account that cannot do it, and `.cl-entry-solo` caps the lone "Join a class" card — `auto-fit` would otherwise stretch it across the whole page around a code field and a button.
- **A classroom is deliberately NOT a `Course`.** A course is a sellable product with a price, a capacity, enrolment holds and a checkout; a classroom is a teaching container with a room, a term, a join code and a curriculum. An earlier plan folded them together and it was wrong: each would end up carrying columns that make no sense for half its rows.
- **The whole point is the foreign key.** A submission is bound to (item, student) by `unique(classroom_item_id, user_id)`, so a file called `final_final_REAL.docx` is still unambiguously that student's work for that assignment. The teacher never reads a filename to work out whose it is. This is the problem statement the portal exists to answer — Google Drive would be storage, not the fix.
- **Join codes drop O/0 and I/1/L.** A code is dictated across a room, and those are the pairs people mishear. `join_code` is deliberately **not fillable** — it is the credential that gets someone into a class, so only the controller may set it — and it is stripped from the API response for anyone who is not the teacher. Matching is case-insensitive and the input uppercases as you type.
- **Assignment and material are one table with a `type`.** They share a title, body, attachments and a place in the feed; only an assignment carries a due date, points and the late rule. Posting a material **forces `due_at` and `points` to null** server-side rather than trusting the client to omit them.
- **Resubmitting REPLACES the files**, it does not stack a second row: there is one piece of work per student per assignment, and two would leave the teacher guessing which to mark. `is_late` is stamped at submit time by comparing against `due_at`, so it stays true even if the teacher moves the deadline afterwards.
- **The grading table lists students who have NOT submitted.** "Who is missing" is the question that screen exists to answer, and a table of only the people who turned up cannot answer it.
- **Files are on the PRIVATE disk**, streamed through a route that re-checks access: the teacher, or the student who submitted it, and nobody else. They are fetched as blobs because the route needs a bearer token, so an `<a href>` cannot reach it — the same reason `MessageAttachment` does it that way. Verified: files present on the private disk, **zero** on the public one.
- **Clicking a file OPENS it; it does not download it.** `components/FilePreview.jsx` (prefix `fp-`) renders images, PDFs, text, audio and video from the blob, with Download always offered and as the *only* option for types a browser cannot render (.docx and friends). Downloading used to be the only behaviour, so marking six submissions meant saving six files to disk and opening them outside the app — and marking is a read-first job. The three call sites (item attachments, the grading table, the student's own submission) all use the one viewer. `kindOf()` checks the stored `mime` **and** falls back to the extension, because an extensionless upload and a missing mime are both real; the three payload shapers now include `mime` so the first check usually wins.
- **Progress is `null`, not 0%, when no work has been set** — 0% reads as failure rather than as "nothing to do yet".
- **The hub is a two-column page, and the right rail is REAL, not padding.** One class alone in the full page width read as an unfinished screen, which is what prompted the rebuild. `ClassroomController::index` now also returns `upcoming` (assignment rows with a `due_at` still ahead, across everything the caller teaches or is enrolled in) and `activity` (curriculum posted, merged with hand-ins received, in one time order, cut to five). Both are **derived from rows the portal already writes** — there is no activity log and no schedule table, and adding one to fill a column would be a second source of truth for something two queries answer. An account with nothing on either is genuinely empty rather than waiting on a feature. **Submissions in the feed are teaching-only**: a student seeing every classmate's hand-in would be a roster leak.
- **The card badges UNGRADED WORK, never the word "Active".** A mockup asked for an Active pill; `index()` only ever returns un-archived classes, so that word would be a constant stamped on every card — decoration wearing a status's clothes. `to_grade` per class is real, changes, and is the thing a teacher needs to see at a glance. It is resolved in **one grouped query**, not one per card. Note the Laravel 9 trap hit building it: handing `pluck()` a `DB::raw` expression as its *value* column throws `Illegal offset type in isset or empty` — alias the count in `select()` and pluck the alias.
- **`1 Students · 1 Assignments` was a real bug and the cause is the documented one**: SQLite returns `withCount` results as **strings**, so `c.students_count === 1` was never true and every card pluralised wrongly. `Number(...)` before the comparison, exactly as the tutor and booking ids need before they are compared against `user.id`.
- **A bare `term` reads as a stray number.** It is free text holding both "Sem 1" and "1", and on a chip row beside a focus and a level that lone "1" told the reader nothing — "Business Based · 1 · HSK 3" was reported as meaningless. `termLabel()` prefixes "Term " **only when the value is nothing but digits**, so a term that already names itself is left alone. The card leads with `subject · level` as its identity line instead, with focus and term demoted to chips beneath the counts.
- **The entry cards are TWO ROWS, NOT THREE COLUMNS, and that was measured.** A mark, copy and an action side by side needs ~400px; these render **441px at 1400**, which left the text column at 166px, wrapped one sentence onto four lines and stretched both cards to **257px tall** (they are 160px now). Gating that on a viewport media query was the wrong instrument as well: `.cl-entry` is an `auto-fit` grid, so the **card** is narrow long before the viewport is. The action sits in column 2 so it starts under the heading that explains it, not under the mark.
- **The role filter only renders when both roles are in play** (`counts.teaching > 0 && counts.studying > 0`). Three pills over a single class is furniture, and a "Studying 0" pill beside it invites a click on nothing.
- **Deliberately NOT built here**: a Private Lessons / Group Classes split on this page. A classroom is not a `Course` (see above), so putting the marketplace's product distinction on the teaching hub would merge two things the schema deliberately keeps apart. There are **no tests for any of this** — `tests/Feature` has no classroom file at all — so the new queries were verified against real rows and, for the paths real data does not reach (a hand-in, a future deadline), inside a rolled-back transaction.
- **Attendance is not built.** The tab renders with a "Soon" chip and says plainly that marking students present per session needs its own record, which nothing in the app produces today. Same treatment as Payment Methods on the profile.
- **Deleting an item removes its files from disk explicitly.** The rows cascade, the files do not — without that they are orphaned forever.
- Item deletion arms on the first click and acts on the second (the pattern Scan's delete uses), disarming on a 4s timer rather than on blur.
- `POST /classes/join` must be declared **before** `/classes/{class}`, or "join" binds as an id — the same trap `bookings/clear-past`, `notifications/read-all` and `articles/recommended` hit.

### Messaging — context-based, never a social network

`conversations` (type `tutor`|`course`, tutor_id, student_id, course_id, last_message_at) + `messages` (conversation_id, sender_id, body, read_at) via `Api\ConversationController`, with `pages/Messages.jsx` (prefix `ms-`) at `/messages`, **laid out from `design/message.png`**: a "Chat" title with a leading accent rule, then a 374 : 591 two-panel split (held as `fr`, so the ratio survives any width — measured 1.58 against the export's 1.58), both panels white with a 1px `#d5d4d9` hairline and 16px corners. Panels are a fixed height and scroll internally, or a long thread walks the composer off screen. The mockup's neutral grey bubbles become **lavender for your own messages**, so the two sides are told apart by colour and not only by alignment. The search box filters the threads you already have — it is not a user search, because there is no directory.

- **The context card is two lines, not one dot-separated run.** It used to read `hsk · Mon, Aug 24, 2:30 PM · 30 min · $12` in flat grey with a solid status block bolted on the left, which gave every fact the same weight and buried the one thing the thread is *about*. Now the lesson name is the card's heading, the when / how-long / how-much sit beneath it in a smaller icon row, and the price is a pill. The status is carried **twice** — a 4px tone rail down the card's left edge and a soft-tinted uppercase pill (`--ms-tone` / `--ms-tone-soft`, set once per tone class and read by both) — so the state is legible from the card's shape before the word is read. Saturated blocks were dropped for tinted pills: four of them stacked against a lavender page read as warning banners. A **course** thread uses the brand tone rather than borrowing "confirmed" green, and its heading is the **level**, not the title — the header directly above is already the course name, and repeating it there would spend the card's one strong line saying nothing new. `.ms-context-link` had been a bare `<a>` with the browser's default underline, which read as unstyled next to everything else; it is now a ghost button with a trailing arrow. `.ms-profile-btn` went the same way — outlined rather than filled, since a solid lavender block in the header fought with the status card immediately beneath it.

- **A thread exists because of a relationship, never a search.** There is no user directory, no "new message" button, and **no student-to-student type at all**. You reach a tutor from their profile or a booking; you reach a course group by being enrolled.
- **One thread per pair, forever.** `firstOrCreate` on (tutor_id, student_id) plus a **unique index** on the pair, so a second, third or tenth booking reuses the same conversation instead of splitting the history. Same for one thread per course.
- **The booking context is DERIVED, not stored.** A pair keeps one conversation across many bookings, so a `booking_id` column on the row would need rewriting on every booking and would be silently wrong the moment that failed. `Conversation::contextBooking()` returns the newest booking between the two, which is always the right "why are we talking?" card.
- **`tutor_profiles.allows_pre_booking_questions`** (default true) gates messaging from someone who has never booked; the profile hides the button entirely rather than offering one that only 403s.
- **Course threads follow enrolment status, not mere existence of a row** — `allows()` checks `held`/`confirmed`, so a cancelled or expired enrolment loses access. Verified: an outsider gets 403, an enrolled student 200, the assigned tutor 200.
- `last_message_at` is denormalised onto the conversation so the thread list sorts by recency without joining messages per row. Opening a thread marks the other side's messages read; **your own messages never count toward your unread badge**.
- **Attachments are on the PRIVATE disk, never `public`.** One file per message (`messages.attachment_path/name/mime/size`), stored under `storage/app/chat/` and streamed by `GET /messages/{message}/attachment`, which runs the same `allows()` check as the thread. A public URL would be readable by anyone who ever obtained it, with no way to revoke — verified: owner 200, unrelated user 403, no token 401, and the file is absent from the public disk. Because the route needs a bearer token, an `<img src>` cannot reach it: `components/MessageAttachment.jsx` fetches the blob and hands the page an object URL, revoking it on unmount so the blob is not pinned in memory. Validated by **extension** (`mimes:`), not sniffed mimetype — the same trap podcast audio hit.
- **A message may be a file with no words.** `send()` requires body OR file, and the bubble is only drawn when there is text, so a picture does not arrive with an empty grey rectangle above it.
- **"Stickers" are emoji**, inserted at the caret rather than appended — a real sticker set would need artwork, licensing and its own storage, none of which helps someone arrange a lesson.
- **Message rows carry the sender's face, and only once per run.** `ConversationController::show` eager-loads `sender.tutorProfile:id,user_id,photo_path` for `sender_photo_url` — both columns are required, `user_id` because the relation matches on it and `photo_path` because the appended `photo_url` accessor reads it. A student has no tutor profile, so their photo is null and the row falls back to an initial, which is correct: this app stores a face only for tutors. Consecutive messages from one person are a single utterance broken into parts, so **only the first of a run wears the avatar**; the rest get `.ms-avatar-gap`, a spacer of exactly the avatar's width, which is what keeps every bubble in a run on one straight left edge instead of stepping in and out. The timestamp hugs its own bubble (`0.1rem`) while rows are separated by `1.25rem` — measured 6.2px against 22px. They were previously 12px and 14px, near-identical, so a timestamp read as floating between two messages rather than belonging to the one above it. Read receipts are per-message `read_at`, which is honest for a two-person thread but only approximate in a course group — real per-member receipts would need their own table and are out of scope.

### Adding a Read topic

**A topic is created by publishing an article with it — there is no topic table and no list to edit.** `articles.category` is validated `nullable|string|max:60` with **no enum**, and the Read page derives its pills and shelves from what has actually been published (`TOPIC_ORDER` first, unknown topics appended alphabetically). So the backend and the page always supported new topics; the only thing preventing one was a hardcoded six-item `<select>` in `ArticleEditDrawer`.

- **The topic field is a combobox** — a text input backed by a `<datalist>`. Type a new topic, or pick one that exists. Native rather than a custom dropdown: keyboard accessible for free, and the entire point is that it accepts a value not on the list.
- **Suggestions come from the shared `articles` cache, not a constant.** That is the same list the Read page and Dashboard already hold, so it costs no request and cannot drift from what is published. `DEFAULT_TOPICS` is only a **floor** for a cold cache. Verified: the field offered "Grammar" — a topic in the data that was never in the hardcoded six.
- **Typed topics are snapped onto an existing one that differs only by case or spacing.** Without it "culture" and "Culture" are two values: two pills, two shelves, and an article filed where nobody looking at the other would find it. Snapping happens on blur AND again on save — Save is reachable without the field ever losing focus (Enter, or clicking straight through), and an un-snapped value would quietly become a second shelf. Anything genuinely new is kept exactly as typed, CJK included.
- Verified end to end: `culture` → `Culture`, `  TRAVEL  ` → `Travel`, `Food and Drink` and `科技 Technology` kept as written, empty still clears back to Unfiled — and "Grammar" already carries both a pill and a shelf, which is the downstream half proving an unlisted topic flows through.

### The Read banner — four slides, one request

`components/ReadHero.jsx` + `.css` (prefix `rh-`), fed by `GET /articles/highlights` (`ArticleController::highlights`). Sits **above** the topic pills, so filtering the library never appears to filter the banner too. Slides: Recommended for you · Pick up where you left off · This week · Verbo Pro.

- **Composition is from supplied references; the palette is Verbo's.** Compact panel, text and CTA left, a visual right. The first flat-`#2b2643` version was rejected as looking "like AI", and the fix was the two things the references all have and it lacked: **a gradient ground and a real illustration**.
- **One gradient for every slide, shared with the Profile hero** as `--hero-gradient` in `fonts.css`. Four per-slide colourways were tried and dropped at the user's request. It is a single token rather than two copies of a three-stop gradient in two stylesheets, for the same reason `SectionToggle`, `EditDrawer`, `ArticleCover` and `ReaderSwitch` were extracted. What distinguishes the slides is the eyebrow, the headline and the artwork — not a tint.
- **Slide classes are `rh-v-article` / `rh-v-week` / `rh-v-pro` — semantic, not colour.** They were originally the tone classes, and removing the tints silently broke two LAYOUT rules riding on them (which slides drop their cover at mid width, and the Pro slide's tighter type). A class that names what a slide *is* survives a restyle; one that names how it looks does not.
- **The CTA is white on `#2b2643`, not dark on `#a89ce3`.** White on lavender measures ~1.9:1, far below readable; on the navy it is **14.37:1**. It also matches the reference banners, whose CTA pills are a darker shade of the banner's own colour, and it separates cleanly from the gradient's dark end where the button actually sits.
- **The illustrations are the app's OWN 3D art** (`profile/graduate.png`, `login/graduate-illustration.png`), already used on Profile and Login — the same cast the learner met at sign-up, not newly sourced stock. They sit bottom-right and are **allowed to run past the panel's lower edge**: an illustration cropped by the card reads as placed in the banner, one floating fully inside reads as pasted on top.
- **`.rh-art` needs `max-width: 100%`.** With only a `max-height` the width is free, and the graduate at 168px tall is wider than the 148px column it sits in — being right-anchored, the excess reached LEFT across the headline and the button. Measured: the art box intersected both the title and the CTA at 985px. The vertical bleed is the effect; a horizontal one is a collision.
- **That bound has a consequence: the COLUMN WIDTH is the size of the illustration**, and `max-height` never binds. At the article slides' 255px the scholar rendered 255x222 inside a 240px panel and read as a small object floating in an empty half — reported as "the illustration looks small". The illustrated slides therefore take a wider column of their own (`.rh-v-week, .rh-v-pro { … 300px }`); the text can afford it, since the Pro headline and its 2x2 benefit grid still fit at ~439px.
- **Crop the books, not the head.** At 300px wide the scholar is 262px tall in a 240px panel, so something must be cut. `bottom: -2.1rem` cut the top — measured **-10.7px of headroom, the mortarboard sliced off**. Pushing the figure down (`-3.4rem`) moves the crop to the books at its feet, which is scenery, and leaves ~12px above the cap. Measured after: no head cut on either slide, 36.1px of bleed below on Pro and 11.4px on This week.
- **THE ARROWS COLLAPSE AWAY AND THE DOTS STAY.** At rest the pill holds only the dots; `.rh:hover` / `.rh-controls:focus-within` opens it. Asked for twice — the first pass only dimmed the arrows to `0.4`, which was the cautious reading and not what was wanted. The accessibility floor is kept without contradicting it: **`:focus-within` covers the keyboard and `@media (hover: none)` keeps them permanently open on touch**, which is the same reasoning that makes the Vocabulary Bank draw its row menu unconditionally. The dots never hide — they are the only thing saying the banner rotates at all, the same argument as the shelf's peeking next card being the affordance.
- **COLLAPSING IS ALSO WHAT FIXED THE "not in the middle" COMPLAINT, and the cause was not alignment.** Measured, the dots and the arrows were BOTH already dead centre (17.72/17.73 and 5.63/5.63) — the arrows are simply what forced the pill to **42px** tall, so six-pixel dots sat marooned in a tall dark box. **`max-width: 0` alone does not do it**: it left the arrows 0 wide and still 30.8px tall, and the pill stayed 42px. With `max-height` collapsing too the pill hugs the dots at **17.84px** and opens to 42.05, so the reveal grows in both directions.
- **That is also what makes easing it safe.** The rule elsewhere is that hover feedback must NOT be transitioned, because a stalled one "leaves the pill looking dead under the pointer" — but nothing here is *revealed by* the transition, so the worst a stalled one can do is leave the controls in their resting look, which is already usable. Observed rather than assumed: in a pane that was not compositing, `.rh:hover` matched while the computed values sat unmoved at `0.28 / 0.4` for the best part of a second. That is the failure mode, and it degraded to "visible and clickable" exactly as intended. `backdrop-filter` stays out of the transition list — static for the same reason the booking dialog mounts already blurred, and the expensive half besides.
- **The resting scrim is 0.28, not lower, and that is the measured finding defending itself.** The pill exists because the inactive dots were measured vanishing into the pale book covers; "it looks heavy" does not make that untrue. So the **arrows** do the receding — two 28px circles are most of the cluster's visual weight — and the scrim only eases off.
- **The controls carry their own scrim because they sit OVER the artwork.** Measured: the art box intersects the controls box, and on Pro the arrows landed on the owl and the books while the inactive dots — white at 0.3 alpha — vanished into the pale book covers. Moving them is not available: the bottom-left is where the tallest slide's CTA already sits, and the art owns the right side by design. The backing is static, with no transition on the `backdrop-filter`, for the same reason the booking dialog mounts already blurred.
- **Slides 1–2 keep the article cover, 3–4 get illustrations.** The cover is specific — it says *which* article — while a ring-plus-bar and a tick list were the two slides that read as a dashboard widget. The progress ring was dropped entirely: a counter and a bar said the same thing twice.
- **Three breakpoints, not two.** Above 1080 both columns at full size; 768–1080 keeps two columns but drops the cover and shrinks the art (the banner lives in the content column, and the sidebar plus two 90px gutters take ~440px, so a 1000px window gives the text only ~296px); below 768 everything stacks and **`.rh-visual` is hidden entirely** — the art is absolutely positioned, so in a stacked layout it escapes its row and lands on the headline. Hiding only `.rh-visual-cover`, as the first version did, left exactly that bug on the two illustrated slides at 375px.
- **One request, not four.** Three or four calls on every visit to this page would hit a bucket React StrictMode already doubles in dev. It also keeps the banner atomic: the slides describe one moment rather than fetches that landed at different times. Its route is declared **before `/articles/{article}`** or "highlights" binds as an id.
- **The height is FIXED at 240px, not a minimum.** The four slides naturally want 272.7 / 230.8 / 215.6 / 230.8, and letting the banner size to each made the whole page jump by up to 57px on every auto-rotate — precisely the distracting movement the brief rules out. The `why` sentence is clamped to one line for the same reason: its length depends on how many reasons scored, so it is the one element that can change the banner's height.
- **Nothing on it is invented.** The recommendation carries the same "Recommended because…" sentence the page already shows; *continue* is the last article actually opened (`article_views`), not a second recommendation wearing a different label; the weekly counts are real queries; and the Pro benefits are the four canonical ones from `Upgrade.jsx`, so the two pages cannot describe different products.
- **`WEEKLY_READ_GOAL` is an APP default and the slide says so** ("Verbo's weekly reading goal"). It is deliberately not derived from `learning_preferences.daily_goal`, which is a duration — converting minutes into a number of articles would be a made-up exchange rate presented as the learner's own goal. Same footing as `Flashcard::MASTERED_STREAK`: a stated rule rather than a felt one.
- **"Continue" is the most recently opened article THAT SLIDE ONE IS NOT ALREADY SHOWING**, not simply the most recent — showing the same article on two of four slides is the real bug. A reader with no history gets the runner-up recommendation tagged `kind: 'suggestion'`, and the client words it "A good place to start" instead of "Pick up where you left off".
- **THE SLIDE CHANGE IS ANIMATED AGAIN — BUT AS A LANDING, NEVER AN ENTRANCE.** `rh-land` on `.rh-text` (440ms, lifts 5px) and `rh-land-art` on `.rh-visual` (520ms, scales to 1.035), both **starting and ending at rest** with the movement only in between — the construction the streak flame established. Stuck at frame 0 is stuck CORRECT, which is the one property an entrance can never have, and it is why this could come back when `rh-in` could not: a fade or a slide would reproduce the original bug exactly. Verified by seeking both to `currentTime = 0` — identity at 0 and at 100%, `translateY(-4.59px)` and `scale(1.035)` at the peak. `.rh-slide` is `display: contents` and generates no box, so it cannot carry this itself; its children remount with its `key`, which is what replays them.
- **The visible slide is React state, never a CSS transition**, and the banner had **NO entrance animation at all** — which is the second half of the frozen-compositor rule rather than an exception to it. It had one: `rh-in`, a transform-only 10px nudge, written on the usual assumption that transform-only is safe because the content stays readable at frame 0. **Readable is not the same as correctly placed.** Measured in a tab that was not compositing, it sat at `translateX(10px)` with `playState: "running"` two seconds into a 320ms run, leaving the text block 11px right of the padding it should sit on — and since some slides settled and others did not, the banner looked subtly misaligned as it rotated. That is what the user saw and reported as "align it". **A transform that never advances still DISPLACES**; the only safe motion is one whose start position is already the resting position, which is no motion. Verified after removal: all four slides at 414.91 against a panel at 385 plus 29.92 of padding, spread 0.00, `transform: none`, zero running animations.
- Auto-rotation is `setInterval` (rAF is throttled to a standstill exactly when a tab is backgrounded), pauses on hover and focus, and does not run under `prefers-reduced-motion`. Verified: rotates, holds while hovered, resumes on leave.
- Below 900px the cover is hidden and the controls return to normal flow — a 232px card beside the text would leave the title in a column too narrow to read, and absolutely positioned controls would sit on the button.

### Podcast resume — where the listener stopped

`podcast_progress` (user_id, podcast_id, position_seconds, duration_seconds, completed_at, unique on the pair) via `PodcastController::saveProgress` (`PUT /podcasts/{podcast}/progress`) and `continueListening` (`GET /podcasts/continue`). `show()` returns the viewer's own `progress` so the player can seek without a second request, and `Podcast.jsx` leads with a **Pick up where you left off** row.

- **Deliberately NOT a column on `recent_views`.** That table is polymorphic and answers one question for the whole app — "what did I touch most recently?" — and a playback position is meaningless for an article, a unit or a scan. The two are complementary and both are written when an episode opens: `recent_views` says you were here, this says where you stopped.
- **`GET /podcasts/continue` must be declared BEFORE `/podcasts/{podcast}`** or "continue" binds as an id — the same trap `bookings/clear-past`, `notifications/read-all`, `articles/recommended` and `classes/join` all hit. There is a test asserting it resolves as a route.
- **The server owns both thresholds, not the client.** `RESUME_FLOOR_SECONDS` (15) — opening an episode and leaving is not a position, and jumping someone back to 0:04 is noise. `FINISHED_WITHIN_SECONDS` (20) — nobody listens through the sign-off, so an episode left at 99% would sit in the row forever. `show()` returns a plain `resume` boolean so the player never reimplements either rule.
- **Finishing is sticky within a run but not permanent**: replaying from the start clears `completed_at`, so a re-listen behaves like a fresh one instead of an episode that can never re-enter the row.
- **Position and duration are clamped server-side.** Both come from the browser and only drive a display and a seek, so the risk is nonsense rather than danger — but a position past the end would sit outside the completion window and strand the episode in "continue listening" for good.
- **The report is on the `<audio>` element's own `pause` event, not in `togglePlay`.** The page's button is not the only thing that pauses audio — media keys, OS media controls and the browser's own UI pause the element directly and never reach a click handler, so a listener stopping with the keyboard would have lost their place. Found by testing: driving `el.pause()` directly wrote no row.
- The timer is `setInterval` at 15s and is **armed only while playing**, so an open-but-paused episode costs nothing against the shared 300/min bucket. `setInterval` rather than rAF because rAF is throttled to a standstill in a background tab, which is exactly when someone is listening with the tab behind something else — same reasoning as the booking hold countdown.
- **Reporting invalidates `podcast:{id}` and `podcasts-continue`.** The episode payload carries `progress`, so a revisit inside the 30s freshness window would otherwise resume from before this session, and the continue row would render its pre-listen state.
- **The resume seek waits for `loadedmetadata`** — a seek before the element knows its duration is silently discarded — and it is **announced**: `.pe-resumed` says "Picked up from 3:21" with a Start over. Being dropped six minutes into an episode with no explanation reads as a bug, not a convenience.
- **The card's progress bar is drawn only when a duration is known.** The client learns it at `loadedmetadata`, so a row written before that has a position and no total, and a bar with an invented denominator would be the one untrue thing on the card.

### Podcast synced transcript — WhisperX offline, import online

Word-timed transcript per episode: the spoken word lights up, clicking a word plays from it. `tools/transcriber/process_podcast.py` (WhisperX, own venv, see its README) writes text + a time per CHARACTER; `App\Services\TimedTranscriptBuilder` turns that into sentence lines of CC-CEDICT words with pinyin/meaning via `DictionaryService::annotate()`; it is stored on `podcasts.timed_transcript` (json, `$hidden`, not fillable) with `timed_transcript_status` (not_processed|processing|completed|failed), `_error`, `_at`.

- **WhisperX never runs on the server.** No GPU, no Python, no queue worker. The admin runs it locally (`php artisan podcast:transcribe {id}` / `--all` for the local DB) and uploads the JSON in the episode drawer's **Sync** tab for production (`POST /podcasts/{id}/timed-transcript`, admin; `GET` for listeners; `DELETE` clears). There is deliberately no "process now" endpoint.
- **WhisperX's own word grouping is ignored** — for Chinese it is one char per "word". The builder maps the dictionary segmentation back onto char timings by index, so `chars` must stay one-to-one with `text`.
- Whisper returns ~30s windows; the builder cuts them into sentences and converts half-width punctuation after Han to full-width (1:1, so indices hold). Traditional -> Simplified happens in Python BEFORE alignment, because the zh aligner's vocab is Simplified.
- Untimed words (digits, Latin) borrow the gap between timed neighbours, split by length, flagged `estimated`.
- A bad upload is refused (422) and the existing transcript survives. Timed saves use `saveWithoutTouching()` — bumping `updated_at` remounts the edit drawer (it is keyed on it).
- **`components/SyncedTranscript.jsx` (prefix `tt-`) never puts the playhead in React state**: flattened sorted timeline, binary search, direct `classList` swaps on two spans. rAF while playing + `timeupdate`/`seeked` for background tabs and paused seeks. Memoised; the page passes stable `useCallback` handlers. Highlight classes are static (frozen-compositor rule). Auto-scroll only when the line leaves the viewport, and pauses 6s after a wheel/touch/key scroll.
- After an import the page patches `timed_transcript_status/_at` in place rather than reloading — a reload with the cache dropped shows the skeleton and unmounts the drawer.

### The reading-aid switch — one control, three pages

`components/ReaderSwitch.jsx` + `.css` (prefix `rs-`) is the Pinyin / Translation switch, used by `ReadArticle`, `PodcastEpisode` and `StudyUnit`.

- **It was extracted because the copies had ALREADY drifted**, which is the same story as `SectionToggle`, `EditDrawer` and `ArticleCover`. `.rd-switch` carried a measured cap-band padding correction (`calc(0.35rem - 1px)` / `+ 1px`) and `.pe-switch` never got it, so the identical control sat a pixel lower on Podcast than on Read. `StudyUnit` had drifted furthest — plain `.un-aid` pills with no switch at all, which is what prompted this. All three now measure 34.09px tall with 4.6/6.6 padding.
- **Values are written out, not read from page tokens.** `--rd-*`, `--pe-*` and `--un-*` all defined these identically (`#e7e3f6`, `#6a6191`, `#a89ce3`, `#726c88`), and reading a per-page variable would reopen exactly the drift the component closes.
- **Each page keeps its own row.** Same split as `PageTools`: the component owns what a switch looks like, the page owns where the row sits — and the rows genuinely differ, since StudyUnit's also holds a play-conversation button.
- **No transition on the knob or the track.** A transition only advances while the tab composites frames, so a sliding thumb would be left at its start position by a backgrounded tab and read as OFF right after being switched on. Same rule as the Settings switch and every `*-in` keyframe here.
- **`StudyUnit`'s play-conversation control is an icon** (`.un-play-all`), not a label — it sat beside two switches whose words are the thing you read, and "Play conversation" was the widest item in the row for an action whose glyph is universal. The name survives in `aria-label` and `title`. It takes its height from `align-self: stretch` rather than naming one: computing it gave 30.4px against a real 31.0, because a line box is not simply font-size x line-height. **`aspect-ratio: 1` does not work for the width** — a flex item's main size comes from its content, so the ratio loses and the button collapsed to 17px wide; symmetric padding around the 14px glyph lands it within 0.9px of square, which at `border-radius: 999px` reads as a circle.

### Link safety — Google Safe Browsing

`App\Services\SafeBrowsingService` + `App\Rules\NoUnsafeLinks`, wired into every endpoint where one user's text is read by another: message send (`ConversationController::send`), article comments, tutor reviews, and a tutor profile's `bio` and `video_url` (both write paths in `TutorController`). Configured by `GOOGLE_SAFE_BROWSING_KEY`.

- **It FAILS OPEN, deliberately.** No key, no network, a slow response, a spent quota — the content is allowed through and the failure is logged. Failing closed would mean nobody in Verbo can send a message because a third party is having an outage, turning someone else's downtime into total loss of communication here. A link filter guards a rare threat; messaging is the product.
- **This is why the request shape has its own test.** A malformed body would earn a 400, get logged, and be allowed through — protection silently off with nothing visibly broken. `test_it_sends_the_request_shape_google_documents` asserts the exact structure Google documents so that failure mode becomes a red test instead.
- **The Lookup API, not the Update API.** Update matches locally against downloaded hash prefixes and keeps URLs private, but needs a background job to maintain that database, and this app runs **no scheduler or queue worker at all** (same constraint that leaves time-based notifications unbuilt). Lookup is one stateless request. The trade-off is real and should be stated rather than hidden: URLs users post are sent to Google. Only URLs, never the surrounding message text.
- **The key is a SECRET and must never get a `VITE_` twin** — unlike `GOOGLE_CLIENT_ID`, which is public by design. Same `configured()` gate as `PaymentService` and `GoogleAuthService`, so a fresh checkout is fully usable with link checking simply off.
- **The URL regex is ASCII-anchored on purpose.** Message bodies here are mostly Chinese, and character classes that run into CJK swallow the sentence around the link. It deliberately over-matches (bare `domain.tld` included, so "Node.js" is looked up) because a false positive costs one cached lookup that comes back clean, while a miss is a live malicious link — the asymmetry is the whole design.
- Verdicts are cached per URL: positives for the `cacheDuration` Google returns (floored at 5 min), negatives for `SAFE_BROWSING_CLEAN_TTL` (default 1h). Keep that in **hours, not days** — a URL clean today can be flagged tomorrow, and caching "safe" for long is how a filter goes quietly stale.

### Running the tests — read this before writing one

**`phpunit.xml` MUST keep `DB_CONNECTION=sqlite` and `DB_DATABASE=:memory:` set.** They ship commented out in the Laravel skeleton, and while they are, the suite inherits `DB_DATABASE` from `.env` — which is `database/database.sqlite`, the real development database. Any test using `RefreshDatabase` then runs `migrate:fresh` against it and **drops every table**.

That has already happened once: it destroyed the local content library and every account, booking, message, flashcard and scan on the machine. Recovery was possible only because two independent copies existed — `backend/backups/*.sqlite` and `backend/database/content/content.json` — and it was still lossy, because the newest backup was five days old and `content.json` is HSK-only by construction (`--skip-level-category=daily`). Both are now uncommitted local artefacts that nothing guarantees; **do not rely on them a second time.**

### Scan (OCR) — environment dependencies

Scan shells out to a local Tesseract binary rather than a paid cloud OCR API. This means the feature depends on machine state that isn't part of the repo:
- **Tesseract OCR** must be installed system-wide (`winget install UB-Mannheim.TesseractOCR`). Path is configurable via `TESSERACT_PATH` in `.env` (defaults to `C:/Program Files/Tesseract-OCR/tesseract.exe` — forward slashes, since Laravel's dotenv parser treats backslashes in double-quoted values as escape sequences).
- **`chi_sim.traineddata`** (Simplified Chinese language data) is not bundled with the Tesseract installer and isn't writable into `Program Files` without admin rights, so it lives project-locally at `backend/storage/tessdata/` instead (fetched from `tessdata_fast` on GitHub) and is passed to Tesseract via `--tessdata-dir` in `OcrService`.
- **CC-CEDICT** (`backend/storage/dict/cedict_ts.u8`, from mdbg.net) is the offline English translation source — no translation API is used. `DictionaryService` parses it into a simplified-word → definition index, cached to `backend/storage/dict/cedict_index.php` (regenerated automatically if deleted). Chinese text has no spaces, so `DictionaryService::segment()` does greedy longest-match word segmentation against this same index before translation/pinyin lookup.
- Pinyin (with tone marks, not numbers) comes from the `overtrue/pinyin` composer package, applied per-segmented-word — not from CEDICT's own numeric-tone pinyin field.
- None of `storage/tessdata/*.traineddata`, `storage/dict/*.u8`, or `storage/dict/*_index.php` are committed (see `backend/.gitignore`) — they're large, machine-fetched assets. A fresh checkout needs Tesseract installed and both files re-downloaded before Scan works.

Supabase (DB/auth) is planned but not yet integrated — no credentials or config exist in this repo. Deployment target is Vercel.

**Known constraint:** the dev machine runs PHP 8.0, which caps Composer to Laravel 9 (EOL). Laravel 10 needs PHP 8.1+, Laravel 11 needs PHP 8.2+. Upgrade PHP before upgrading Laravel major versions.

```
npm install       # install deps
npm run dev       # dev server at http://localhost:5173
npm run build     # production build
npm run lint      # ESLint
npm run preview   # preview production build
```

### Backend (`backend/`)
```
composer install                  # install deps
php artisan serve                 # dev server at http://127.0.0.1:8000
php artisan test                  # run test suite
php artisan test --filter=NameOfTest   # run a single test
php artisan migrate                # run DB migrations
```

Backend `.env` is not committed — copy `backend/.env.example` to `backend/.env` and run `php artisan key:generate` on a fresh checkout.

### The floating practice assistant — Gemini behind Laravel

`components/PracticeAssistant.jsx` + `.css` (prefix `pa-`), mounted once in `Layout`, talking to `POST /practice-chat` (`Api\PracticeChatController` → `App\Services\GeminiService`).

- **THE KEY NEVER REACHES THE BROWSER.** React → Laravel → Gemini → Laravel → React. `GEMINI_API_KEY` is server-side only and must never get a `VITE_` twin — same rule as `GOOGLE_SAFE_BROWSING_KEY`, the opposite of `GOOGLE_CLIENT_ID`. A test asserts the key appears nowhere in the response body, and another asserts an upstream 400 carrying `API key AIzaSy… is invalid` is logged rather than returned.
- **It is mounted in `Layout`, and that IS the feature.** The component never unmounts as you move between Read, a podcast and a study unit, so the conversation is still there when you reopen it — verified across a real in-app navigation. Per-page mounting would reset the thread on every click.
- **Unlike `SafeBrowsingService`, this FAILS CLOSED.** That one guards a rare threat while messaging is the product, so it must never block a send. Here the answer *is* the product: a learner who asks a question and silently gets nothing has been lied to. Failures return 503 with a plain sentence the widget shows as a bubble in the thread — not a banner, because it is a reply to what was just asked.
- **`configured()` gates the whole thing.** `GET /practice-chat/status` is asked once on mount and an install with no key renders **no button at all**, rather than one that only ever errors.
- **Its own rate-limit bucket, `ai`, at 15/min.** Every other endpoint costs a query; this one spends a metered third-party quota shared by the whole install, so at the general 300/min one person could burn the day's free tier. Keyed by user id, never IP — the route is behind `auth:sanctum`, and keying by IP would make one campus share an allowance.
- **`topic` is `in:`-validated against `PracticeChatController::TOPICS`.** It is interpolated into the system brief, so a free-text topic would let a caller append their own instructions to the prompt. The chips ship in the status response so the client list cannot drift from the validator's.
- **Nothing is stored.** The thread lives in the widget's state and is re-sent (trimmed to `MAX_HISTORY`, 12) each turn. A saved chat is a new data domain — history, deletion, who-can-read — and none of it helps someone asking "is this sentence right?" mid-article. The trim is also the cost bound: the whole history goes up every turn.

**THE DRAG IS A TRANSFORM ON A SEPARATE ELEMENT, and both halves of that were learned by measuring.**
- Writing `left`/`top` with everything divided by `--app-scale` — the conversion `WordPopover` needs — was **right sideways and wrong downwards**: the painted rect came back at `1.1045x` the written `left` but `1.1837x` the written `top`. A zoomed ancestor is a containing block for a fixed child, so those offsets are not simply the viewport scaled. A translation has no origin to get wrong, so only the *delta* is converted: one divide, nothing assumed.
- **Clamping is done in painted pixels**, where the rect and `window.innerWidth/Height` are already the same units, then solved back into the translation — that is why the clamp sits on that side of the divide.
- `.pa-anchor` carries the drag offset and `.pa` inside it carries the open animation, because **one element owning both transforms changed category on the FIRST drag** and landed it 11.7px off the pointer while every later drag was exact. Verified after the split: four drags exact including the first, and two deliberately off-screen drags clamp to the edge.
- `setPointerCapture` is wrapped in try/catch: it throws when the pointer is already gone, and an uncaught throw there abandons the drag before it starts.

**Animation follows the app's frozen-compositor rule, so "fade-in" is a rise.** The brief asked for fading messages; every keyframe here is **transform-only** instead, because an animation advances only while the tab composites frames and one starting at `opacity: 0` leaves the content permanently invisible — the bug that once blanked the account popover. The typing indicator's dots start and end at their resting position and only bob in between, so a frozen compositor shows three visible dots rather than none.

- The font stack leads with Hellix and falls through to `PingFang SC`/`Microsoft YaHei`/`Noto Sans SC` — Hellix carries no CJK at all, and this is a window whose content is Chinese.
- The mic is the browser's own `SpeechRecognition` at `lang: 'zh-CN'`, and **renders nothing where the browser lacks it** rather than offering a button that does nothing. Its result fills the draft rather than sending, so a misheard sentence can be fixed first.
- Minimise and close both return to the one small button; the difference is the thread, which minimise keeps and close clears.

**Pinyin is CHECKED, not trusted** — `App\Services\PinyinCorrector`, run over every reply before it leaves `GeminiService`. Reported as "sometimes it gets the pinyin wrong", and intermittently wrong is the worst kind: a learner cannot tell which lines to trust, so every line becomes untrustworthy. Verbo does not have to guess — `DictionaryService` already derives tone-marked pinyin from CC-CEDICT deterministically, and it is what Read, Podcast and Study all render, so the assistant now answers from the same source as the rest of the app.
- **It corrects tones, not style.** The dictionary spaces every syllable (`nǐ jīn tiān`) while the model groups them into words (`Nǐ jīntiān`), and the model's grouping reads better. The comparison strips spacing, case and punctuation, so a line is replaced **only** when the syllables or tone marks actually differ.
- **Both shapes the model uses are handled**: pinyin on the next line, and bracketed on the same line (`你好！(nǐ hǎo)`). The bracketed one is what actually turned up in the report, and the first version missed it entirely.
- **Recognition is against the EXPECTED pinyin, not the look of the line.** An earlier version required a tone mark to identify pinyin at all, which meant `Ni hao` — pinyin with the tones simply missing, one of the errors worth catching — was skipped as though it were English. Stripping tones off both sides settles it exactly: `Ni hao` and `nǐ hǎo` both bare to `nihao`, while `Hello there!` matches nothing and is left alone. **That last case is the one that must never go wrong**, and it has its own test, as does a bracket holding a note rather than pinyin.
- Two bugs worth remembering, both found by probing rather than reading. **`foreach ($lines as $i => $line)` walks a COPY**: this pass writes to `$lines[$i + 1]`, so on reaching that line foreach handed back the stale original and wrote it over the correction — every fix was made and instantly undone. Iterate `array_keys()` and read `$lines[$i]`. And the inline regex required only whitespace between the characters and the bracket, so **every sentence ending in a full-width `！` or `？` was skipped** — the gap has to allow punctuation.
